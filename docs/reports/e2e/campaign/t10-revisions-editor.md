## Подшаг (е): Escape/blur посреди ручной правки

Изолированный эксперимент (два раунда, чтобы отличить autosave-по-debounce от autosave-по-Escape):

1. Раунд 1: выделен фрагмент, введён текст `ESCAPETEST_DRAFT`, **сразу** (без Escape) проверен DOM — черновик виден в DOM, но **API ещё не видит** правку (не проверялось изолированно в раунде 1, см. раунд 2). После `press Escape` — API уже видит правку (ревизия **318**, `hasEscapeDraft: true`).
2. Раунд 2 (контрольный, чтобы исключить debounce-autosave): выделен новый фрагмент, введён `SECONDPROBE`, **сразу** проверен API — **черновик НЕ сохранён** (`hasSecondProbe: false`, current всё ещё 318). Только после `press Escape` — новая ревизия **319**, `hasSecondProbe: true`.

**Вывод**: Escape в TipTap-редакторе **коммитит** черновик как полноценную сохранённую ревизию (эквивалент blur), а НЕ отменяет его. Черновик никогда не теряется молча — критерий PASS формально выполнен («не теряется молча»). Но это отклонение от общепринятой UX-конвенции (Escape = отмена/discard, не commit) — зафиксировано ниже как находка **F-T10-3 (LOW, UX)**. Скрин: `19-escape-commits-draft.png`. Консоль чистая на обоих раундах.

## Находки

**F-T10-1 (MEDIUM, расширение T3-F4 — новая детализация, не новый баг).** T3-F4 задокументировал стейлость панели Revision History только после Refine. Этот прогон показывает: стейлость (панель не рефетчится без полной перезагрузки страницы, хотя верхний score-чип и баннер обновляются live корректно) воспроизводится ТАКЖЕ после:
  - ручного редактирования абзаца (manual-edit, PATCH `/api/paragraphs/{id}`) — op1, op5, подшаг (а);
  - Evaluate — подшаг (в);
  - document-level Accept-all (bulk, множественные `apply-edit`) — op8.

  И **НЕ воспроизводится** (панель рефетчится мгновенно, без reload) после:
  - одиночного Accept одного issue — op2b;
  - Restore (любой — 3-я строка, best, restore-of-restore) — op4, op7, restore-of-restore;
  - document-level Reset — op6.

  Гипотеза root cause (не проверялась в коде, только поведенчески): фронтенд, похоже, явно триггерит рефетч истории после accept/restore/reset-эндпоинтов, но не после edit/evaluate/refine/accept-all-эндпоинтов — то есть баг не привязан к «мутирует ли текст» (accept и manual-edit оба мутируют текст, но ведут себя по-разному), а к тому, какой конкретно API-путь дергается на фронтенде. Данные на бэкенде корректны и не теряются ни разу — это чисто клиентский недостающий рефетч. Не блокирует, но затрагивает больше путей, чем было известно.
  Артефакты: `06-after-evaluate-noreload.png`/`07-after-evaluate-reloaded.png`, `08-op1-manual-noreload.png`, `10-op3-refine-noreload.png`/`11-op3-refine-reloaded.png`, `13-op5-manual2-noreload.png`, `16-op8-acceptall-noreload.png`/`17-op8-acceptall-reloaded.png`.

**F-T10-2 (LOW/MEDIUM, корроборация T3-F1).** Одиночный Accept на issue с устаревшим/пересекающимся фрагментом (issue 182, op2a) тихо возвращает 422 от `/api/paragraphs/58/apply-edit`, но клиент всё равно помечает issue как `accepted` через отдельный `PATCH /api/issues/182` — карточка исчезает из списка без тоста/баннера, отличить «применено» от «устарело-но-помечено-принятым» в UI невозможно. Тот же паттерн воспроизведён ВТОРОЙ раз в этом прогоне на p65 во время Accept-all (op8, 2× 422 на issues 148/149) — подтверждает, что это системный, не однократный баг. Артефакты: `09-op2-accept-422-silent.png`, консоль-дамп с 422 в op8.

**F-T10-3 (LOW, UX-квирк, новая находка).** Клавиша Escape во время ручного редактирования абзаца в TipTap-редакторе **коммитит** текущий черновик как сохранённую ревизию (`origin=edit`), а не отменяет его — нарушает общепринятую конвенцию (Escape = discard/cancel). Данные не теряются (даже более безопасно, чем ожидалось), но поведение может удивить пользователя, ожидающего отмены правки клавишей Escape. Изолированно подтверждено двумя раундами (типирование без Escape не сохраняет; после Escape — сохраняет). Артефакт: `19-escape-commits-draft.png`, `t10-p58-escape-draft.txt`.

## Не найдено (проверено, чисто)

- **Paste HTML→БД**: чисто, без HTML/скриптов в данных, XSS-канарейка не выполнилась. См. подшаг (б).
- **Restore-на-current**: честный disabled, не дубль-ревизия.
- **Restore-of-restore**: не плодит дубли, не циклит, не крэшит.
- **Два таба одной сессии**: единое консистентное состояние в обе стороны, без конфликтов/форков.
- **Reset архивирует, не удаляет** live-скоры/issues (согласуется с явным текстом confirm-диалога и Hard Invariant «Never delete LLM predictions»); revision-ledger для p58 вырос с 4 до 24 записей за прогон, ни одна не удалена.
- Ни одной ПОТЕРЯННОЙ правки за весь прогон (8 операций цепочки + edge-кейсы + escape-тест + paste-тест + два таба) — каждая мутация текста трекнута отдельной ревизией, воспроизводима через `t10-p58-op*.txt`.

## Ран / не ран

- **Ран**: (а) manual edit; (б) paste rich text + санитизация; (в) Evaluate; (г) полная цепочка из 8 операций с проверкой истории до/после reload на каждой; (д) restore-of-restore (дважды) + restore-на-current; (е) Escape-коммит (два изолированных раунда); (ж) два таба одной сессии в обе стороны. Все live, прод `https://glossa-mt.com`, собственный session-isolated клон БД (`glossa_sid`), `X-Golden-Session` не использовался ни разу.
- **Не ран**: TTL-уборка неактивных сессий (4ч ожидания) — вне бюджета прогона, сознательно не тестируется по протоколу кампании (см. спека § Протокол исполнения п.6). Параллельная нагрузка N>2 одновременных пользователей на один документ — вне скоупа T10 (это T3/T7). - **Прерывание и возобновление**: операция 2 цепочки (г) была прервана обрывом харнесс-сессии на середине первой попытки Accept; возобновлена в ТОЙ ЖЕ playwright-cli сессии (`-s=t10`, cookie/клон сохранились) без потери прогресса — см. раздел «Технический инцидент прогона» выше. Ни один под-шаг, завершённый и записанный ДО инцидента (baseline, (а), (б), (в)), не переигрывался.
