## 4. Ручной расчёт агрегата (обязательный пункт PASS-критерия)

Формула (`src/palimpsest/webapp/aggregate.py`): для каждого **enabled**-критерия,
чьё значение присутствует, `norm = (value − scaleMin) / (scaleMax − scaleMin)`,
затем `aggregate = round(Σ(norm·weight) / Σ(weight) · 10, 2)`. Критерии без значения
(здесь — упавший Terminology) исключены **и из числителя, и из знаменателя** — не
занулены, а полностью выброшены из формулы.

На момент evaluate у paragraph 117 действовали веса 0.32/0.24/0.24/0.2 (все enabled),
но Terminology не вернул значение (см. находку №1), поэтому в сумму вошли только 3:

```
accuracy: value=6.0, scale=[1,10] → norm=(6.0-1)/9=0.55556, w=0.32 → 0.17778
fluency:  value=7.0, scale=[1,10] → norm=(7.0-1)/9=0.66667, w=0.24 → 0.16000
style:    value=4.0, scale=[1,10] → norm=(4.0-1)/9=0.33333, w=0.24 → 0.08000

num = 0.17778 + 0.16000 + 0.08000 = 0.41778
den = 0.32 + 0.24 + 0.24 = 0.80        (Terminology НЕ входит в den, т.к. failed)
aggregate = round(0.41778 / 0.80 · 10, 2) = round(5.2222, 2) = 5.22
```

API вернул `"aggregate": 5.22` — **сходится с точностью до 4 знаков**. Формула
математически устойчива к любой сумме весов (это средневзвешенное, не сырая сумма),
поэтому гипотетический риск спеки «веса не нормируются → агрегат врёт» **не
воспроизводим в принципе** — подтверждено чтением `aggregate.py`, а не только этим
одним прогоном с уже нормированными к 1.0 весами. Честно отмечаю: сценарий с
намеренно не нормированной суммой весов (например, оставить 1.2) на живом evaluate
я не прогонял — риск закрыт чтением кода, а не отдельным прогоном (см. §7 «не
тестировалось»).

## 5. Находки

### №1 — CRITICAL: кастомные критерии в принципе не оцениваются (заявленная фича статьи мертва)

Каждый вызов `/evaluate` для кастомного критерия падает **до обращения к LLM** с
`FileNotFoundError`, т.к. `judge.py::_scoring_prompt()` жёстко читает промпт из файла
`prompts/scoring/{criterion_id}.md`:

```python
def _scoring_prompt(criterion_id: str) -> str:
    return (paths.PROMPTS / "scoring" / f"{criterion_id}.md").read_text(encoding="utf-8")
```

В `prompts/scoring/` реально лежат только `accuracy.md`, `fluency.md`, `style.md` —
подтверждено `ls`. Для любого нового `id` (например `crit-1784280057251`) файла нет.
**Поле `prompt`, которое пользователь вводит в форме «Add judge» и которое честно
сохраняется в БД (`CriterionBody.prompt` → `INSERT INTO criterion(...prompt...)`),
нигде не читается** — судья всегда использует не то, что ввёл пользователь, а
хардкод-файл по id, которого для кастомного критерия не существует. Корень
воспроизведён прямым чтением файловой системы:

```
$ python3 -c "from palimpsest.paths import PROMPTS; print((PROMPTS/'scoring'/'crit-1784280057251.md').exists())"
False
```

Это НЕ transient-ошибка (`FileNotFoundError` не входит в `is_transient_error()` в
`llm/client.py`), поэтому падает с первой попытки, без ретраев — ровно то поведение,
что наблюдалось live (2/2 попыток: исходный Evaluate и Retry failed, оба падают
идентично, `shots/11-para2-evaluated.png` и `shots/15-retry-failed-again.png`).

**Последствие для продукта:** заявка статьи §2.2 «add any arbitrary criteria»
демонстрируется UI-формой, которая выглядит полностью рабочей (поле Prompt с
textarea, Save, чип в тулбаре, строка в Ranking) — но результат для пользователя
100%-но недостижим. Это хуже отсутствующей кнопки (которую предвидело решение
владельца #2): кнопка есть и обещает функциональность, которую код не реализует.

**Severity: CRITICAL.** **Repro: 2/2, детерминированно.**

### №2 — MEDIUM: ошибка сурфейсится, но с «сырым» внутренним id вместо имени критерия

В инспекторе абзаца **есть** красный баннер с кнопкой ретрая:

```
Failed: crit-1784280057251   [Retry failed ↻]
```

(`shots/11-para2-evaluated.png`, `shots/14-terminology-disabled-chips.png`). Это
хороший сигнал (я изначально ошибочно решил, что сигнала нет вообще — исправляюсь
здесь явно), но текст показывает внутренний `id` (`crit-1784280057251`), а не
человекочитаемое имя «Terminology» — для реального пользователя, добавившего
критерий через UI, это нечитаемо и не объясняет, ЧТО именно не работает.

**Severity: MEDIUM.**

### №3 — MEDIUM: та же ошибка нигде не сурфейсится за пределами инспектора конкретного абзаца

В Scores-табе (`shots/12-scores-tab.png`) и в Ranking-табе (`shots/13-ranking-4criteria.png`)
неудачный критерий показан просто как «—» — **визуально неотличимо от «ещё не
оценивался»**. Проверено `el.getAttribute('title')` на ячейке — `no-title-attr`,
тултипа нет. Пользователь, просматривающий Ranking по всем абзацам (а не
конкретную карточку с баннером), не увидит вообще никакого сигнала, что колонка
Terminology систематически не работает.

**Severity: MEDIUM.**

### №4 — LOW: DELETE вернул 204, а не ожидаемый по сюжету 409

Спека (шаг е) предполагала проверку защиты «критерий с историей score/issue нельзя
удалить» (`app.py::delete_criterion` — `409 "criterion has score/issue history;
disable instead"`). У Terminology **никогда не было ни одной успешной оценки**
(находка №1), поэтому в таблицах `score`/`issue` для него нет строк — `DELETE`
прошёл 204. Логика 409-гарда прочитана и подтверждена по коду (SQL-запрос
`SELECT 1 FROM score WHERE criterion_id=? UNION SELECT 1 FROM issue WHERE
criterion_id=? LIMIT 1`), но **не проверена живым прогоном** — удалять
`accuracy`/`fluency`/`style` (у которых есть история) для теста нельзя: это
нарушило бы инвариант «никогда не удалять LLM-предсказания»
(`.claude/rules/invariants.md`). Честно фиксирую как непроверенный вживую путь.

**Severity: LOW** (сама защита выглядит корректной по коду; просто не была
триггернута этим прогоном по объективной причине).

### №5 — MEDIUM: precompute нового документа сразу упал с `budget_exhausted`, несмотря на живой $0.41/$100000 бюджет

После создания документа `{"status": "stopped", "done": 0, "planned": 3,
"succeeded": 0, "errorReason": "budget_exhausted"}` — при этом
`GET /api/budget` в этот момент показывал `spentUsd=0.41`, `capUsd=100000` (бюджет
почти не тронут). Причина найдена в коде: `precompute.py::_take_call_slot()`
использует **процесс-глобальный, не привязанный к сессии** счётчик
`budget._STATE["precompute_calls"]` с лимитом `_CALL_CAP=80`
(`PALIMPSEST_PRECOMPUTE_CALLS`). Т.к. на проде параллельно с T8 шли другие сценарии
мега-кампании (сессии `t4`, `t10`, `fable-acceptance` были одновременно открыты —
подтверждено `playwright-cli list`), их precompute-вызовы делят один и тот же
глобальный лимит на 80 вызовов за весь процесс, а не за сессию/документ. Мой
документ просто попал под уже исчерпанный чужими сценариями лимит. Это совпадает
с уже известной находкой из памяти («T2: precompute silent 5/8 fail») — тот же
корень, ещё одно подтверждение.

**Severity: MEDIUM** (сама фича «warm the cache» для нового документа непригодна
для использования во время параллельной кампании; в обычном единичном использовании
проблема не проявится, но лимит стоит либо поднять, либо привязать к сессии/документу).

### №6 — LOW, recurring: double-DELETE по одному клику подтверждения

Клик по «Remove» на строке Terminology породил **два** нативных `confirm()`-диалога
(`playwright-cli requests` показал два ожидающих модальных состояния с одинаковым
текстом «Delete "Terminology"?») и после одного `dialog-accept` — **два** DELETE-запроса
подряд (оба вернули 204, т.к. операция идемпотентна). Это уже известный по памяти
паттерн (`translation-demo-bugs.md`: «double-DELETE per confirm... 5th run») —
здесь это уже как минимум **6-е** подтверждённое срабатывание в разных местах
Settings (ранее — в реестре моделей). В этот раз конкретно безвредно (204/204), но
для операции без идемпотентной защиты на бэкенде (например, если бы вторая DELETE
попадала в гонку с другим клиентским действием) это может стать реальным багом.

Контрольная проверка: DELETE документа T8 в конце прогона (тот же паттерн
подтверждения) отработал **один раз** — двойного клика не было. Т.е. баг
воспроизводится не на 100% кликов, а нестабильно (вероятно, двойная привязка
обработчика к конкретно кнопке Remove в развёрнутой строке критерия).

**Severity: LOW** (в этом прогоне безвредно), но стоит завести как системный тикет —
это не первый раз.

## 7. Что запущено, а что нет — явно

**Запущено (живой прогон, LLM-вызовы реальные):**
- полный happy-path (а)–(е) кроме прямой проверки самой рубрики Terminology на
  реальном анахронизме (физически невозможно из-за находки №1);
- disable/enable критерия через чекбокс, PUT-верификация;
- retry упавшего критерия;
- delete критерия + восстановление весов + GET-дифф;
- cleanup документа + верификация golden-документа.

**НЕ запущено, с причиной:**
- Проверка 409 при удалении критерия с реальной историей score/issue — не
  запускалась намеренно, т.к. единственный способ получить такую историю на проде —
  удалить один из `accuracy`/`fluency`/`style`, что нарушает инвариант «никогда не
  удалять LLM-предсказания». Логика подтверждена чтением кода (`app.py::delete_criterion`),
  не живым вызовом.
- Живой evaluate с намеренно НЕ нормированной суммой весов (>1.0) — я перенормировал
  веса ДО первого evaluate, поэтому фактически на проде такой edge case не
  триггерился. Закрыт анализом формулы `aggregate.py` (устойчива к любой сумме `den`
  by construction), но не отдельным замером.
- Причина, по которой сама рубрика Terminology («мэр Вавилона» → «king») никогда не
  была реально проверена LLM-судьёй — заблокирована находкой №1; косвенно
  подтверждено, что accuracy/fluency/style сами независимо поймали проблему с «mayor»
  (issue explanation: «The word 'царь' means 'king'… translating it as 'mayor' is a
  major factual error»), так что тестовые данные (payload) были содержательно верными
