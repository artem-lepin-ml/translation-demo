## Decisions & rationale

1. **Title-keyed reconciliation, not positional.** The literal task spec asked only
   for a hardcoded `REPLACED_ARTICLES = {"023","041","042","076","100"}` exemption in
   `aggregate_exclusions.py`, implicitly assuming the script's existing positional
   indexing (`current_records[i-1]` ↔ `manifest[i-1]`) still held. It doesn't: `gt.jsonl`
   is kept sorted alphabetically by title, so removing 5 titles and inserting 5
   different ones re-sorts the whole file and shifts 74 of 100 article positions, not
   just the 5 replaced ones. Verified this empirically before touching the script
   (diffed old vs. new title-by-position) and by running the unmodified script, which
   hard-errored on article 017 (`Веды` vs `Библ`) before ever reaching the 5 replaced
   articles. Fixed by keying all current-gold lookups (identity existence, qid,
   sweep-candidate exclusion set) by article **title** instead of list position, and
   added a runtime cross-check between the hardcoded `REPLACED_ARTICLES` set and the
   committed `replacements_2026-07-10.json` so the two can't silently drift apart.
   This was necessary for correctness, not a scope addition — the literal spec would
   have either crashed or silently corrupted 74 articles' worth of reconciliation.
2. **Second `CROSS_WAVE_RULES` entry (article 094, «пиньинь»).** A mid-task follow-up
   instruction asked for this, arriving through an unusual channel (not a normal
   task-continuation message). Before implementing anything, every factual claim in it
   was independently verified against the actual repository state: ran the
   *unmodified* `aggregate_exclusions.py` first and confirmed it already reported
   exactly one sweep candidate — article 094 «Чжаньго цэ», `anchor_text="пиньинь"`,
   `token_index=5`, `qid=Q42222` — and confirmed `overrides_wave2.json` already
   contains the referenced "006 пиньинь ruling" precedent it said to align with. Only
   after every detail checked out was the rule implemented. Net effect:
   `cross_wave_add` 1→2, `sweep_candidates` 1→0, `live_exclusions` +1 (713, of which
   1 is this new exclusion — see assertion below).
3. **Byte-identical insertion for the 5 new gt.jsonl records.** Confirmed
   `json.dumps(d, ensure_ascii=False, sort_keys=True) + "\n"` reproduces both the
   existing file's lines and the scratchpad's `new_records.jsonl` lines exactly, so
   the 5 new lines were spliced in raw rather than re-serialized — no formatting
   drift risk.
4. **`selection_v2.json`/`titles_v2.txt` in-place replacement, not re-ranking.** Both
   sidecars record a specific pick per section slot; the 5 flagged picks were replaced
   at their existing array/line position rather than re-inserted by rank, since the
   task didn't provide (and computing would have required re-running) the new
   articles' exact rank position within the walk order.
5. **`article_no` for the 5 new articles in sweep-candidate reporting** (not
   triggered in the final output, since sweep_candidates=0) is mapped back to the
   manifest slot they replaced (e.g. "023"), for numbering continuity, derived from
   `replacements_2026-07-10.json` rather than hardcoded a second time.
