3 Что сделано

Цель. Третий eval-датасет для секции evaluation статьи EMNLP 2026 (industrial track, ru→en перевод: пайплайн + нормализация терминологии + LLM-judge&refinement). Три датасета: том историко-энциклопедического перевода (Данил), BOUQUET (Данил, 198 абзацев), wiki-100 (этот воркстрим, 100 статей ру-Википедии, 2553 абзаца) — без референсных переводов, только QE-метрики + judge, с мостом к таблице BOUQUET-чисел Данила.

Ключевые решения и почему

Путь A: гоняем репозиторий Данила как есть
Не портируем пайплайн в src/palimpsest/evaluation/ (явная не-цель спеки) — паритет с BOUQUET-числами важнее архитектурной чистоты; наш репо добавляет только экспорт корпуса, sidecar, статистику/корреляции, QE-раннеры и обвяз, код Данила не дублируется.
Primary-судья: fixed-J вместо вербатима Данила
qwen3_6-27b, temp 0, thinking off (вместо temp 0.7 / thinking on у Данила) — детерминизм и защита от «тройного конфликта» (Qwen3.6 судит себя, рефайнит всех, пересуживает свои правки). Вербатим-конфиг сохранён в пилоте и пробах (test-retest, J′, BOUQUET-ре-ран с двумя judge-колонками) — решение измеряется, не постулируется. Требует подтверждения руководителя (Д2, см. блок 6).
Скрипт корреляций сначала провалидирован, потом доверяем
scripts/judge_metric_stats.py прогнан на вендоренных BOUQUET-выходах Данила до применения к wiki: 23/24 ячейки Спирмена совпали точно, что подтвердило чтение формата (какой вариант MetricX, какое выравнивание). Обнаружен ceiling-эффект (потолок |ρ| ≈ 0.5–0.7 при 80%+ массы judge-оценок в 9–10) — поэтому основной дизайн анализа на wiki это paired-дельты с предрегистрированными порогами ничьей, а не сырой Спирмен.
Вырожденные абзацы не ветвим, а фильтруем на анализе
37 абзацев ≤3 токенов («Источники», «Комментарии») переводятся и судятся как есть (выравнивание индексов), но исключаются из корреляций/paired-анализа фильтром на этапе анализа, с sensitivity-прогоном с/без фильтра — раскрыто в лимитациях статьи.

4 Критичные находки и недоделки

CRITICAL — метрик качества по нашим четырём моделям пока нет ни одной. Живой смоук 2026-07-07 проверял только механику API (перевод + парсинг judge-ответов), не качество перевода. В облаке нет GPU — ни один прогон vLLM, MetricX или CometKiwi не выполнялся; вся содержательная часть эксперимента ждёт sr004 (§ 6, дорожная карта).
HIGH — чекпоинты MetricX и COMET, которыми пользовался Данил для BOUQUET-таблицы, нигде не названы в вендоренном коде (`external/gse-translation` содержит только форматы входов/выходов, не сами скрипты подсчёта). Наш выбор чекпоинтов для wiki может не совпасть с его — до ответа его и наши колонки MetricX/COMET не смешиваются в одной таблице без пометки (вопрос Д1, письмо ниже).
HIGH — одна ячейка Спирмена не воспроизвелась: Qwen3.6 Accuracy × Comet у Данила −0.0690, у нас на его же вендоренных данных −0.0069 (остальные 23/24 ячейки — точное совпадение до 4-го знака). Наиболее вероятная причина — описка на лишний/пропущенный ноль в скриншоте, но это вывод по данным, не подтверждённый напрямую с Данилом (часть письма ниже).
HIGH — выбор primary-судьи fixed-J (qwen3_6-27b, temp 0, thinking off вместо вербатима Данила temp 0.7 / thinking on) сделан нами, но ещё не подтверждён руководителем (Д2). Не блокер для старта пилота (вербатим-конфиг и так сохранён в пробах), но если руководитель потребует вербатим как primary — потребуется пересчёт с другим конфигом на уже собранных данных.
HIGH — runbook `docs/stages/translation-eval.md` + `patches/` для sr004-обвяза ещё не закоммичен (готовится параллельно этому отчёту). До коммита doc-parity по CLAUDE.md Hard Invariant 2 не закрыт для этой части работы.
INFO — `scipy` не добавлен в зависимости проекта (`pyproject.toml`/`uv.lock` не тронуты умышленно, чтобы не расширять диф): `scripts/judge_metric_stats.py` запускается только через `uv run --with scipy`, обычный `uv run` без флага упадёт на импорте.
INFO — для `scripts/judge_metric_stats.py` нет unit-тестов: скрипт сделан и заявлен как одноразовый валидационный инструмент, тесты не запрашивались в задаче.
INFO — отбор пилотных статей по «децилям» — решение с развилкой (ранговое разбиение 100 статей на 10 равных по счёту корзин vs подбор по значению-полусумме границ перцентилей); выбран ранговый вариант как стандартный смысл термина и как более воспроизводимый. Альтернатива расходится сильно в длинном хвосте (децили 8–9 дают непересекающиеся наборы статей) и дёшево пересчитывается тем же скриптом, если понадобится.
INFO — «короткий» smoke-абзац в наборе индексов — буквально самый короткий во всём корпусе, но это однословный фрагмент-заголовок («Периодизация:», 1 токен), слабый кейс для проверки качества перевода. Стоит заменить на более представительный короткий абзац перед реальным smoke translate-прогоном на sr004.
