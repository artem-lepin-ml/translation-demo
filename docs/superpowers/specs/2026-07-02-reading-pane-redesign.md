## Дизайн-решения

### 1. Компактный гуттер со счётом

Сейчас: колонка `va-para-gutter` шириной 72px на каждый абзац (§N + вертикальный чип со score и дельтой) съедает прайм-полосу по всей высоте документа ради ~20px полезной информации.

Решение: **мета-строка абзаца** (paragraph meta strip, высота ~24px) над телом абзаца, на всю ширину обеих панелей. Содержит один горизонтальный компактный чип:

```
[§2  8.0 ▲0.4]      … (cached)
```

- `§N` — 11px, `--va-text-dim`, tabular-nums (как сейчас).
- Score — 12px bold, цвет по полосе: green ≥ 8 / yellow ≥ 6 / red < 6 (маппинг `scoreBand` из [store.ts:578](../../../frontend/src/demo/store.ts#L578)).
- Дельта `▲0.4` / `▼0.3` — 10px, green/red, появляется только при ненулевой дельте (логика `computeChipDelta`/`deltaBadge` из [EditorParagraph.tsx:216](../../../frontend/src/demo/variant-a/EditorParagraph.tsx#L216) не меняется).
- `cached`-бейдж — как сейчас, в хвосте чипа.
- Loading-состояние: `…` с пульсацией на месте score; мета-строка продолжает показывать shimmer во время eval. (rev-3: режимов больше нет — мета-строка живёт в единственном сегодняшнем layout'е `EditorParagraph`, над телом абзаца.)
- `[M]` Абзац без оценки (`aggregate === null`, не loading): мета-строка всё равно рендерится, на месте score — em-dash `—` тем же кеглем; ширина чипа стабильна (нет layout-сдвига при появлении первой оценки).
- `[M]` CSS-неймспейс: в приложении НЕ вводится параллельный неймспейс — компактный чип реализуется как `va-`-классы (`.va-para-meta`, `.va-para-chip` + модификаторы полос `.green/.yellow/.red`). Классы `.a-*` в макете — локальная стенография макета, в код не переносится (см. «Расхождения макета со спекой»).

Попутный фикс: в текущем CSS классы полос на чипе НЕ стилизованы — `ScoreChip` вешает `va-score-chip green|yellow|red` ([EditorParagraph.tsx:241](../../../frontend/src/demo/variant-a/EditorParagraph.tsx#L241)), но правил `.va-score-chip.green/.yellow/.red` в [variant-a.css](../../../frontend/src/demo/variant-a/variant-a.css) нет — число рендерится дефолтным цветом. В новом чипе цветовая семантика обязательна; `[M]` тест — юнит по классам полос (green/yellow/red для 8.0/6.4/5.7) + проверка фактического цвета (computed style) в браузере на этапе скриншотов (jsdom не резолвит `var()` из внешнего CSS — см. «Влияние на тесты»).

Эффект: обе панели получают обратно по ~36px ширины каждая; мета-строка стоит ~24px вертикали на абзац (абзацы пилота — 4–13 предложений, это <3% высоты абзаца). Мета-строка также служит визуальным разделителем абзацев и кликабельной зоной выбора абзаца (селектор `.va-para-row.selected` сохраняется).

`[M]` Пустой документ (0 абзацев): область абзацев рендерит существующий empty-state паттерн (центрированный muted-текст, как loading-state в [VariantA.tsx:267](../../../frontend/src/demo/variant-a/VariantA.tsx#L267)); заголовки колонок остаются.

### 3. Адаптивные заголовки панелей + унификация имён

Сейчас: hardcoded `Original ({sourceLang.toUpperCase()})` / `Translation ({targetLang.toUpperCase()})` ([VariantA.tsx:433](../../../frontend/src/demo/variant-a/VariantA.tsx#L433)). После параллельного воркстрима языки — произвольный свободный текст («Russian», «German»), `.toUpperCase()` даст «RUSSIAN».

Принятая конвенция (применяется по всему UI): пользовательские ярлыки — **«Source»** и **«Translation»**; в коде/API остаются идентификаторы `source_*` / `target_*`.

- Заголовки: `Source · Russian` / `Translation · English`.
- Резолвер имени языка — `langLabel(raw: string): string` (первый шаг lookup'а — словарь код→имя из upload-polish, он сохраняется):
  1. если `raw` соответствует BCP-47-форме (`isBcp47Like`: `/^[a-z]{2,3}(-[A-Za-z0-9]+)*$/i`; rev-3: функция нужна только display-пути — резолюция локали сегментации отменена) — `new Intl.DisplayNames(['en'], { type: 'language' }).of(raw)` в try/catch;
  2. иначе (свободный текст) — как есть, с заглавной буквы;
  3. фолбэк при любой ошибке — исходная строка.
- **Принятая граница поведения** (CRITICAL-2): 2–3-буквенный свободный текст («she», «foo») неизбежно ложно матчится BCP-47-регексом. `Intl.DisplayNames` с дефолтным `fallback: 'code'` на well-formed-но-неизвестном коде возвращает вход как есть → пользователь видит свой же текст, катастрофы нет; на malformed-входе try/catch отдаёт raw (подтверждено эмпирически на re-review: 'she'/'foo' echo verbatim, Node 25). Принимаем: 2–3-буквенные строки трактуются как коды; компромисс осознан и зафиксирован юнит-тестом (`langLabel('she')` — без исключения, непустой результат; допустимы оба исхода: echo или ISO-имя, если такой код существует).
- **Разрешение merge-конфликта с `feat/upload-polish` (HIGH-2; rev-3 — обновлено)**: upload-polish **уже влит в `dev-demo`** — «конфликт» выродился в обычный ребейз ветки на `dev-demo`. `dev-demo` содержит `frontend/src/demo/lang.ts` со словарным `langLabel` `{ru: 'Russian', en: 'English'}` (только код→имя) и импортирует его в `VariantA.tsx`/`GlossaryTab.tsx` — ровно те call-sites, которые правит эта фича. Наша реализация (`isBcp47Like` + `Intl.DisplayNames`) **замещает** тело `langLabel` ВНУТРИ того же `lang.ts`, словарь сохраняется как ПЕРВЫЙ шаг lookup'а (до `Intl.DisplayNames`); call-sites не меняются. (rev-3: обратный словарь имя→код НЕ добавляется — он был нужен только отменённой резолюции локали сегментации.)

### 4. Режим чтения «предложение-в-строку» с выравниванием

> ⚠️ **ОТМЕНЕНО (rev-3, решение владельца 2026-07-02):** aligned-вид не делаем; раздел целиком (вкл. сегментацию, резолюцию локали и несовпадение числа предложений) сохранён только как дизайн-история.

Каждое предложение с новой строки; предложение i источника и предложение i перевода вертикально выровнены; высота ряда = max двух сторон (если левое предложение занимает 3 строки, следующее предложение обеих сторон стартует с одного y). Абзац остаётся атомом оценки.

#### Сегментация предложений

Утилита `segmentSentences(text: string, locale?: string): SentenceSpan[]` (форму `SentenceSpan` см. в контракте segment-model):

- основной путь — `Intl.Segmenter(resolvedLocale, { granularity: 'sentence' })`;
- фолбэк (нет `Intl.Segmenter` в рантайме) — regex по стандартной пунктуации `/[^.!?…。！？]+(?:[.!?…。！？]+["»')\]]*|$)/gu`;
- финальный шаг алгоритма (оба пути): **сегменты с пустым `text.trim()` отбрасываются** — они не порождают рядов;
- `[M]` **деградация**: ЛЮБАЯ ошибка сегментации (исключение, пустой результат на непустом тексте) → весь абзац как одно «предложение» `[{ text, start: 0, end: text.length }]`; рендер никогда не блокируется;
- `[M]` крайние случаи (в юнит-листе): пустая строка → `[]`; строка из одних пробелов → `[]` (0 рядов, следствие отброса пустых); текст без финальной пунктуации → один сегмент на весь текст.

#### Резолюция локали сегментации (CRITICAL-2)

`sourceLang`/`targetLang` — свободный текст, НЕ обязательно BCP-47. `new Intl.Segmenter('Russian')` бросает `RangeError`; макет прогонял только `'ru'`/`'en'`, поэтому путь свободного текста требовал явной спецификации. Алгоритм `resolveSegmenterLocale(raw: string): string | undefined`:

1. lookup в минимальном обратном словаре имя→код, входящем в **эту** фичу (MEDIUM-3: в upload-polish такого маппинга НЕ существует — он хранит сырые строки и умеет только код→имя): `{russian: 'ru', english: 'en', german: 'de', french: 'fr', spanish: 'es', italian: 'it', portuguese: 'pt', chinese: 'zh', japanese: 'ja', arabic: 'ar'}`, ключи lowercase, живёт в том же `lang.ts` (~10 записей, без обобщений);
2. иначе если `isBcp47Like(raw)` (та же функция, что в `langLabel` — single source of truth) — вернуть `raw`;
3. иначе — `undefined` → `Intl.Segmenter(undefined, …)` (root-правила).

Плюс страховка: сам вызов конструктора всё равно в try/catch с ретраем на `undefined` (регекс-валидатор не гарантирует валидный тег).

**Известная лимитация**: root-локаль (`und`) не знает локале-специфичных исключений для сокращений — на кириллических «г.», «в.», «н.э.» при свободном тексте вне словаря возможно пере-разбиение предложений. Честно: для свободнотекстовых загрузок язык вне 10-словника — **частый случай, не edge case**; деградация до root-локали — штатный режим с косметическими последствиями (лишние ряды), не ломающий. Замер на пилоте (локаль `ru` доступна): «1400 г. до н.э.» сегментируется корректно.

Юнит-тесты локали: `locale='Russian'` (не бросает, работает через root), `'ru'`, `'de-DE'`, `undefined`, `'!!!'` (malformed → root), окружение без `Intl.Segmenter` (regex-фолбэк).

#### Несовпадение числа предложений

Пары строятся строго i↔i; хвостовые лишние предложения продолжаются непарными рядами (пустая противоположная ячейка с меткой `no pair`), без принудительного спаривания и без падений. Замер на пилоте: 7 из 16 абзацев имеют разное число предложений (напр. §3: 4 RU против 6 EN) — непарные хвосты это **частый случай**, не edge case. Принятое ограничение: при слиянии/разбиении предложений переводчиком выравнивание после точки расхождения монотонно съезжает — это косметика чтения, не разметка соответствий, и цена принята.

`[M]` RTL: порядок панелей фиксированный (source слева), `dir="auto"` на каждой ячейке (как сейчас на `.va-para-source/.va-para-target`); RTL-языки заявленно не тестировались — за пределами скоупа, кроме этой пометки.

### Segment-model: контракт и алгоритм (CRITICAL-1)

> ⚠️ **ОТМЕНЕНО (rev-3):** segment-model не реализуется — `review-extension.ts` остаётся как есть; контракт сохранён для истории.

У `Issue` **нет оффсетов** — только `targetFragment`; спаны находятся `findOccurrences(paraText, targetFragment)` по всему тексту абзаца и **могут пересекать границы предложений**. В aligned-grid такой спан физически разрывается между двумя рядами. Контракт, закрывающий это:

```ts
// segment-model.ts — plain-text offsets ONLY, никаких PM-позиций.

export interface SentenceSpan {
  text: string;   // срез текста абзаца
  start: number;  // [start, end) в тексте абзаца
  end: number;
}

export interface TermSpan {
  termId: string;
  start: number;
  end: number;
  side: 'source' | 'target';
  difficulty: 'green' | 'yellow' | 'red';
  pairAccuracy: 'green' | 'yellow' | 'red' | null;
  pairIndex: number;
}

export interface ElementarySegment {
  start: number;             // [start, end) в тексте абзаца
  end: number;
  issueIds: string[];        // отсортированы по criterionId (стабильный порядок цветов, как сейчас)
  underlineColors: string[]; // цвета покрывающих критериев, параллельно issueIds
  term: TermSpan | null;     // термы не перекрываются между собой; charStart/charEnd из API
                             // применимы ТОЛЬКО к side='source'; для side='target' оффсеты
                             // выводятся внутри buildSegments через findLeftmost(targetSurface)
  sentenceIndex: number;     // какому ряду грида принадлежит сегмент
}

export function buildSegments(
  text: string,
  issues: Issue[],           // резолюция substring→offset происходит ЗДЕСЬ, внутри segment-model
  terms: TermSpan[],
  sentences: SentenceSpan[],
  criterionColors: Record<string, string>,
): ElementarySegment[];
```

Алгоритм `buildSegments` (расширение сегодняшнего `buildDecorations` из [review-extension.ts:109](../../../frontend/src/demo/variant-a/review-extension.ts#L109)):

1. Резолюция оффсетов — **внутри** segment-model: для каждого open-issue `findOccurrences(text, issue.targetFragment)` (все вхождения, как сейчас); вызывающий код передаёт сырые `Issue[]`, а не оффсеты.
2. Множество границ = концы issue-спанов ∪ концы терм-спанов ∪ **границы предложений** (`start`/`end` каждого `SentenceSpan`).
3. Элементарные сегменты между соседними границами; для каждого — покрывающие issue (по midpoint, как сейчас), терм, и `sentenceIndex` (бинарный поиск по `sentences`).
4. Спан, пересекающий границу предложения, автоматически распадается на ≥2 сегмента с **одинаковым `issueIds`** — клик по любой части открывает тот же `IssuePopover` (делегация по `data-issue-ids` не различает части).

**Визуальная непрерывность разрезанного спана** (решение): обе части несут те же stacked-underline цвета — подчёркивание «продолжается» на следующем ряду, как перенос подчёркнутого текста на новую строку, это сам по себе достаточный аффорданс; дополнительно hover по любой части подсвечивает ВСЕ сегменты с тем же `data-issue-ids` в абзаце. Механизм — явно как у term cross-highlight, т.е. **React-state-driven, не чистый CSS**: новое состояние `hoveredIssueIds: string[] | null` протягивается так же, как сегодняшний `hoveredTermId` (delegated mouseover ставит state, рендер вешает класс подсветки на совпадающие сегменты). Отдельного глифа «continues» не вводим — визуальный шум без новой информации.

Тесты: юнит — синтетический issue-фрагмент через границу предложений → ровно 2 сегмента, `issueIds` идентичны, `sentenceIndex` соседние; e2e-скриншот кейса — план скриншотов, № 13.

`[M]` Скоуп: segment-model обслуживает ровно двух потребителей — aligned-рендер и PM-декорации. Никаких «pluggable boundary sources» и обобщений впрок.

`[M]` PM-адаптер: пересчёт plain-text-оффсетов в позиции ProseMirror (`base = paraOffset + 1`) остаётся ТОЛЬКО в `review-extension.ts`; segment-model про PM не знает. Паритет-тест покрывает границу адаптера: на данных §1 пилота декорации, построенные из `buildSegments`, совпадают по позициям/классам с текущим `buildDecorations`.

`[M]` Мемоизация: `segmentSentences` + `buildSegments` мемоизируются на абзац с ключом `(text, issues, terms)` (`useMemo` в компоненте ряда); пересчёт только при реальном изменении входов.

### Инвариант источника текста (HIGH-C)

> ⚠️ **ОТМЕНЕНО (rev-3) как отдельное требование:** grid-рендера больше нет; общий принцип «текст — из store» и так выполняется текущим кодом (sync-эффект `initialText`).

**Единственный источник текста — store (`document.paragraphs[idx]`), никогда — живое PM-состояние.** `sentences` и `segments` выводятся синхронно из одного и того же снапшота абзаца в одном рендере — смешение старых оффсетов с новым текстом исключено по построению (между текстом и разметкой нет асинхронного шага). Пока `paraEvalState[idx].loading === true`, grid продолжает рендерить прежний layout (текст в store ещё не менялся), shimmer только на чипе; старые оффсеты с новым текстом не смешиваются никогда. Тестируемое утверждение: юнит на компонент ряда — при `loading=true` и неизменном тексте DOM сегментов не меняется (snapshot-равенство), меняется только чип.

### Шов режимов: контракт (a)–(e) (HIGH-A)

> ⚠️ **ОТМЕНЕНО (rev-3):** режимов нет — правка остаётся всегда живым TipTap, шов не существует; `editingParaIdx`/flush-протокол не реализуются.

   - *За toggle*: Flow-рендер — это существующий путь `EditorParagraph`, который ОБЯЗАН жить ради Edit-режима в любом случае, поэтому предельная стоимость toggle мала (кнопка + localStorage + пара e2e-сценариев); Flow — привычный сплошной вид для вычитки связности абзаца целиком и страховка, если сегментация на новой языковой паре поведёт себя плохо.
   - **Рекомендация**: оставить toggle (дефолт Aligned) — низкая предельная стоимость при реальной страховочной ценности; рост e2e ограничиваем: полная матрица только для Aligned, для Flow — smoke (рендер + правка одного абзаца). Ждёт решения владельца.
