## 1. Цель и не-цели

**Цель.** Дать для статьи третий eval-датасет компонента «LLM-as-a-judge + refinement» в **безреференсном** сеттинге:
на 100 статьях ru-Википедии для 4 моделей измерить качество перевода до/после refinement тремя LLM-метриками
(Accuracy / Fluency / Style, 1–10) и двумя автоматическими QE-метриками (MetricX-24-QE, CometKiwi-22),
посчитать согласованность judge×метрики (Спирмен + paired-анализ), и отдать:
(а) две таблицы уровня статьи (качество систем; корреляции), (б) per-paragraph JSONL
(source, translation, 5 метрик) в формате хэндоффа Данила/Андрея, (в) case study / error analysis,
(г) прогон тех же 4 моделей на BOUQUET-абзацах для пересечения таблиц с Данилом («побольше пересечения по моделям»).

**Не-цели:** не гипотезный тест с pass/fail-планкой качества переводов; не дальнейшая чистка/курирование корпуса;
не файнтюн моделей; не rolling-context перевод (отдельная абляция вне скоупа); не замена оценки Данила на томе
энциклопедии; не решение паритета с Данилом при заблокированном В1 (тогда сетапы публикуются как разные — § 10 п.6).

## 4. Пайплайн прогона

### Ф0 — Probe (обязательный gate перед любым платным объёмом)

Зеркало «Ф1 — Triage» из model-comparison, расширенное на локальные серверы. Прогоняется на 3–5 абзацах
(короткий/средний/максимальный из корпуса):

1. **Локальные серверы**: все три vLLM-процесса подняты одновременно, round-trip по одному запросу на каждый;
   для TG — проверка формата репака и вменяемости перевода на 3 абзацах растущей длины (спот-чек глазами);
   для Qwen3.6 — в ответе нет `<think>` и `usage.completion_tokens` без reasoning-надбавки.
2. **deepseek-v4-flash**: 10 проб на маршрут — 2xx-доля, честность prompt-токенов, `usage.reasoning_tokens == 0`
   (или ограниченно малый); если модель на маршруте думает — ищем request-выключатель или переоцениваем бюджет § 7 и
   помечаем асимметрию сетапа для статьи.
3. **Судья J**: маршрут реально принимает `temperature=0` (3 идентичных промпта → квазиидентичные ответы);
   `usage.reasoning_tokens == 0`; фактическая цена из `usage.cost_usd` сверяется с каталожной, реальная цена J
   подставляется в § 7 (механизм уже есть: `webapp/budget.py::_load_prices()`).
4. Результаты пробы — в `docs/experiments/<slug>/probe.md`; **непройденная проба блокирует фазу translate**.

### Ф1–Ф5 — основной цикл (per model × per paragraph)

1. **Translate** — независимый перевод абзаца (без rolling-контекста: паритет с BOUQUET-сетапом Данила и
   независимость сэмплов для корреляций). Промпт: TG — нативный delimiter-формат репака; остальные —
   [prompts/translator/default.md](../../../prompts/translator/default.md). Sampling: TG greedy (по card),
   Qwen — non-thinking параметры card, deepseek — T=0.3 (как в демо; проба Ф0 подтверждает отсутствие thinking).
   Гард TG-контекста: `tok(template)+tok(paragraph)+max_new_tokens ≤ 2048`, иначе `max_new_tokens` снижается
   либо абзац помечается `tg_ctx_overflow` (в meta.json; ожидаемо ~0 случаев, max абзац ≈ 600–800 ток).
   Ретраи: `complete_retrying` 6×(1..60с) как у wiki-eval; абзац, упавший после всех ретраев, помечается
   `translate_failed` и исключается из всех последующих фаз (не молча: счётчик в meta.json).
2. **Judge (initial)** — фиксированный судья J (единый для всех систем; § 11 В2) оценивает тремя промптами
   [prompts/scoring/](../../../prompts/scoring/) → `final_score` 1–10 + `identified_issues` на каждый критерий;
   `severity` выводится `derive_severity()`; каждому issue проставляется поле `criterion` (по промпту-источнику).
3. **Refine** — [prompts/correction/system.md](../../../prompts/correction/system.md): Source + Translation +
   issues, сгруппированные по критериям (контракт промпта), → исправленный перевод. Рефайнер = та же система
   (self-refine, паритет с «Refined» Данила), кроме TG (§ 11 В3). Статус в записи — `refine_status ∈
   {ok, skipped_no_issues, failed_after_retries}` (никакого перегруженного bool); `failed_after_retries`
   исключается из paired-анализа § 5.
4. **Judge (refined)** — те же 3 промпта тем же J. В CLI это отдельный запуск `judge --stage refined`
   со своим чекпоинтом (§ 6).
5. **QE-метрики** — на initial И refined: MetricX-24 (`google/metricx-24-hybrid-xxl-v2p6-bfloat16`, `--qe`,
   `--max_input_length 1536`, `batch_size ≥` числа видимых GPU — известный баг деления батча) и CometKiwi
   (`Unbabel/wmt22-cometkiwi-da`, gated CC-BY-NC-SA). На BOUQUET дополнительно ref-based:
   MetricX-24 без `--qe` + `Unbabel/wmt22-comet-da` (Apache-2.0).
6. **Длинные абзацы — обязательный гард.** Оба скорера **молча** обрезают вход (MetricX: конкатенация
   source+candidate(+reference) до 1536 mT5-токенов; COMET: 512 XLM-R-токенов на сэмпл, source+mt вместе).
   По пре-оценке в окно COMET не влезают лишь самые длинные абзацы (p90=123 слова ≈ 350–450 XLM-R-токенов
   парой — влезает; хвост распределения ближе к max=392 слов — нет); точная доля меряется пре-токенизацией
   на исполнении. Правило: абзац сверх лимита → предложенческий сплит (razdel / nltk для EN) с длинно-взвешенным
   средним по кускам; доля таких абзацев логируется в `meta.json` и раскрывается в статье. Никогда не поднимать
   `--max_input_length` выше обученного (README-варнинг MetricX).

**Вызовы J**: CloseRouter, пин маршрута, `temperature=0`, `max_tokens=1024` (JSON скора+issues), строгий JSON
с ровно одним corrective re-ask; **антидум-гард на ВСЕХ путях** (translate/judge/refine): ответ с `<think>`
или reasoning-полями → хард-фейл попытки (ретрай, не молчаливый strip), счётчик `thinking_leak` в meta.json.
`max_tokens` по типам: translate 2048 (TG — по остатку 2K-бюджета), judge 1024, refine 2048.
Bias-note: J не должен совпадать ни с одной оцениваемой системой (self-preference); если владелец выберет
deepseek-v4-flash как J — deepseek-строки помечаются в статье как self-judged (§ 11 В2). Робастность к судье:
на подвыборке ~100 абзацев refined-переводы дополнительно оценивает второй судья J′ ≠ J, репортится agreement
(закрывает «а согласился бы другой судья» — § 9 circular-риск).

## 5. Метрики, корреляции и анализ (по методологической записке)

- **Таблица 1 (качество):** 4 системы × {initial, refined} × {Accuracy, Fluency, Style, MetricX-QE↓, CometKiwi↑}
  (+ для BOUQUET колонки MetricX-ref↓, COMET-ref↑). Средние + bootstrap 95% CI (ресэмплинг по абзацам).
- **Таблица 2 (согласованность):** Спирмен 3 judge-оси × 2 QE-метрики × 2 датасета (12 ячеек, как у Данила), с:
  (а) знаком MetricX, явно инвертированным (raw MetricX должен коррелировать **отрицательно**);
  (б) tie-rate / доля модального значения judge на ячейку; (в) отдельно pooled и within-system
  (де-мин по системе; защита от парадокса Симпсона).
- **Paired-анализ (главная added value):** Δjudge vs Δmetric на refinement (та же система, тот же абзац):
  sign-agreement (3×3 win/tie/loss), Kendall tau-b по дельтам, bootstrap CI по абзацам.
  **Предрегистрация:** ничья = |Δjudge| < 1 (минимальный шаг шкалы) / |Δmetric| < 0.25 MetricX-балла
  и < 0.01 COMET (порог ≈ полуширина сегментного шума, уточняется на пилоте Ф0 и фиксируется ДО основного прогона);
  критерий успеха анализа: sign-agreement на не-ничьих парах > 60% с 95% CI, не накрывающим 50%, или tau-b > 0
  со значимостью по бутстрэпу. **План Б, если paired-анализ тоже нулевой:** основной квантитативный аргумент
  статьи смещается на (а) tie-rate/стабильность judge как самостоятельный вывод, (б) agreement J×J′,
  (в) кейс-стади с разбором расхождений; это фиксируется как заранее заявленная ветка, не пост-хок.
- При ceiling-эффекте judge (у Данила 80%+ масс на 9–10) потолок |ρ| ≈ √(3p(1-p)) ≈ 0.5–0.7 даже при идеальном
  согласии — околонулевые Спирмены ожидаемы теоретически; в статье подаём это как объяснение, а не оправдание.
- System-level корреляция (4 системы) — только описательно: n=4 не достигает значимости в принципе (min p=2/24≈0.083).
- Гистограммы распределений judge-скоров и метрик — в отчёт и приложение статьи.
- Кейс-стади по образцу FactOWL: таблица разобранных вручную расхождений judge×метрика с колонкой «доказательство»
  (цитата source/translation), 8–12 строк; **правило отбора раскрывается**: top-N по |Δjudge−Δmetric| (нормированные)
  + 3–4 случайные строки — не ручной черри-пик; + примеры удачного/неудачного refinement.

## 6. Реализация в репо

- Новый модуль **`src/palimpsest/evaluation/`** (stage-конвенция «один stage = один модуль»):
  `translate.py` (обёртки промптов систем + TG-контекст-гард + think-гард), `judge.py` (адаптер 3 рубрик:
  парсинг `final_score`+`identified_issues`, `derive_severity()`-реюз, проставление `criterion`),
  `refine.py` (группировка issues по критериям + correction-вызов), `chunking.py` (пре-токенизация
  и предложенческий сплит для QE-гарда), `qe.py` (subprocess-оркестрация MetricX/COMET: JSONL-in/JSONL-out,
  ненулевой exit-code = фейл фазы, чекпоинт на батч), `stats.py` (корреляции/paired-анализ; scipy),
  `report.py` (чистый оффлайн-рендер таблиц/HTML — зеркало wiki-eval `report.py`).
- CLI **`scripts/translation_eval.py`**: `probe` / `translate` / `judge --stage {initial,refined}` / `refine` /
  `score-qe` / `report` — раздельные идемпотентные фазы, каждая со своим чекпоинтом
  (`translate.partial.jsonl`, `judge_initial.partial.jsonl`, `judge_refined.partial.jsonl`, …) и `--resume`;
  `meta.json`, `model_slug`-директории `reports/translation-eval/<slug>/<run_id>/`.
- **BudgetGuard покрывает ВСЕ платные вызовы**: `kind ∈ {translate, judge, refine}` (расширение существующего
  extract/judge-паттерна) — deepseek-translate/refine и все вызовы J проходят `reserve()/settle()`.
  `--max-judge-calls` **переопределяется явно** (унаследованный дефолт 900 ≈ в 80 раз мал): для варианта A ставим
  80 000; дополнительно `--max-usd` на каждый запуск. **Сквозной кап между фазами/корпусами:** каждый запуск
  при старте читает суммарный `spend` из meta.json всех предыдущих фаз эксперимента (по каталогу эксперимента)
  и сидирует BudgetGuard остатком от общего капа владельца (В6) — паттерн `--resume`-сидирования, поднятый
  на уровень эксперимента. Второй эшелон — лимит на ключе CloseRouter (В6).
- **Проводка сэмплинг-параметров (обход дыры `from_model_config`):** конфиги моделей в `evaluation/`
  конструируют `LLMConfig` напрямую с `extra_body` (`top_k`, `presence_penalty`,
  `chat_template_kwargs={"enable_thinking": false}` для Qwen3.6 и т.п.); через `models.yaml`/`from_model_config`
  эти параметры НЕ проводятся (он их молча теряет — § 0).
- Конкурентность: судья J — отдельный семафор; повышение с дефолтных 4 до 8–12 идёт по прецеденту
  `--llm-workers` (ticket 004, owner-approved) и **утверждается владельцем** (В10); локальные vLLM-вызовы
  капом CloseRouter не связаны (свой семафор на сервер).
- Выходной per-paragraph JSONL (формат хэндоффа Данила/Андрея): `{dataset, article|par_id, par_idx, source,
  translation_initial, translation_refined, scores: {accuracy, fluency, style} × {initial, refined},
  metricx_qe × 2, cometkiwi × 2, issues[] (с criterion), refine_status, chunked_for_qe: bool,
  judge_model, judge_provider, usage}`.
- MetricX/COMET — не вендорим: раздельный venv на A100-ноде (у MetricX пины 2023 года — `transformers==4.30.2`,
  Python 3.10; конфликтует с vLLM-окружением) + git-clone `google-research/metricx`. В репо — раннер-скрипт
  и полный runbook в `docs/stages/translation-eval.md` (doc-parity в том же коммите, Hard Invariant 2).
- Отказоустойчивость локальных серверов: фазы translate/refine перед каждым батчем пингуют health-endpoint
  vLLM; смерть сервера = пауза фазы с сообщением, `--resume` продолжает с последнего чекпоинта после ручного
  рестарта сервера (in-flight абзацы не теряются — записи чекпоинтятся по завершении абзаца, как в wiki-eval).
- Доступы (чек-лист перед прогоном): HF-логин + gates: `google/translategemma-27b-it` (manual — запросить сразу
  после утверждения спеки), `facebook/bouquet`, `Unbabel/wmt22-cometkiwi-da`; `OPENROUTER_API_KEY` (CloseRouter) на ноде.

## 7. Оценка объёма (вариант A: полный корпус, 2 553 ¶)

Состав judge-вызова: системный промпт рубрики ≈ 900–1300 ток (accuracy 91 стр / fluency 119 стр / style 94 стр,
шлются verbatim каждый вызов) + абзац-пара ≈ 250–500 ток (mean/p90) → **~1.5–2.2k in / ~0.3k out** на вызов;
оценки ниже взяты по верхней границе с явным запасом ~10% (паттерн model-comparison). Если провайдер J
поддерживает prompt-caching — фактический in-спенд ниже; в оценку не закладываем.

| Фаза | Вызовов | Где | Оценка |
|---|---|---|---|
| Translate | 2 553 × 4 ≈ 10.2 к | 3 локально + deepseek API | локально часы; deepseek ≈ $1–2 |
| Judge initial + refined | 2 553 × 4 × 2 × 3 ≈ **61.3 к** | CloseRouter (J) | ≈ 130M in / 20M out ток. → flash-lite-класс ≈ $15–25; frontier-класс (если ~$0.30/$0.30 — **цена проверяется пробой Ф0**, не постулируется) ≈ $45–60 |
| Refine | 2 553 × 4 ≈ 10.2 к | 3 локально + deepseek API | локально часы; deepseek ≈ $1–2 |
| MetricX-QE + CometKiwi | (2 553×4×2) × 2 ≈ 41 к скорингов | локально (1×A100) | GPU-часы, $0 |
| J′-робастность (~100 ¶ refined × 4 × 3) | ≈ 1.2 к | CloseRouter | ≈ $1–3 |
| BOUQUET (все фазы на 320 ¶) | 320×4×2×3 ≈ **7.7 к** judge + 2.6 к translate/refine | — | ≈ +12–15% к бюджету |

Тайминг (консистентная тройка вызовы×латентность×конкурентность): 61.3 к × ~2 с = ~34 ч последовательно;
при конкурентности 4 → **~8.5 ч**, при 8 → ~4.3 ч. Вывод: 3 дней достаточно с большим запасом уже при C=4;
повышение до 8–12 (В10) — оптимизация, а не необходимость. Локальный translate+refine: ~20 к генераций на
3 сервера — часы. Вариант B (~1 000 ¶) делит judge-бюджет на ≈2.5.
Жёсткие капы: `--max-usd` на запуск + сквозной кап эксперимента (§ 6) + лимит ключа; итог задаёт владелец (В6).

## 9. Риски

- **Несопоставимость с числами Данила**, если его judge-модель/промпты отличаются от наших реконструированных —
  снимается только доступом к GitLab-коду (В1) или фиксацией судьи вместе с ним (В2). До этого таблицы Данила и
  наши публикуются как разные сетапы одного компонента (и это отражено в § 10 п. 6 как явный исход, не молчание).
- **Репак TG ≠ официальные веса** (third-party): до основного прогона — спот-чек 3 переводов репака против
  референсного прогона официального чекпоинта через `transformers` (доступ manual-gate); точный шаблон промпта
  логируется в meta.json. Расхождение → офиц. чекпоинт через transformers-бэкенд (медленнее, но верно).
- TranslateGemma 2K-контекст: гард-формула в § 4 Ф1; refinement для TG — открыт (В3).
- Thinking-протечки (Qwen3.6, deepseek, потенциально J) → гард на всех путях (§ 4), проба Ф0, счётчики в meta.json.
- CloseRouter ~90%/маршрут → resilient-ретраи 6×(1..60с) + пин маршрута + `FailureTracker`; предположение
  «транзиентный фейл не биллится» проверяется на Ф0 по `usage.cost_usd` фейл-ответов; так или иначе
  `settle()`-сверка по факту — второй контур.
- Смерть локального vLLM-сервера mid-run → health-чек + resume-контракт (§ 6).
- Gated-модели: TranslateGemma — manual approval, может занять время → запросить доступ сразу после утверждения спеки.
- Judge-двойная роль (скоринг и issues для refinement) → circular-flavor: мера — раскрытие в limitations,
  QE-метрики как независимый контроль дельты И **J′-робастность на подвыборке** (§ 4) как независимый судья.

## 10. Критерии успеха

1. Проба Ф0 пройдена и заархивирована (probe.md) ДО первого платного объёма; все маршруты/серверы подтверждены.
2. Per-paragraph JSONL по 4 системам × 2 стадиям на wiki-корпусе (+BOUQUET при В9-ок), с meta.json и полным
   учётом спенда по kind (translate/judge/refine — ни одного неучтённого платного вызова).
3. Таблицы 1–2 + paired-анализ (с предрегистрированными порогами) + гистограммы; числа воспроизводимы
   `report`-фазой оффлайн.
4. Доля обрезанных/сплитнутых абзацев в метриках и все thinking-leak/fail-счётчики задокументированы;
   ни одного молчаливого трима или молчаливого исключения.
5. Кейс-стади (8–12 строк, раскрытое правило отбора) + фигура «демка↔методология» готовы для статьи.
6. Сопоставимость с Данилом: либо подтверждена (В1/В2 закрыты — единый судья/промпты, таблицы объединяемы),
   либо ЯВНО оформлена как «разные сетапы» в тексте статьи — никогда не смешано молча.
7. Спенд ≤ капа владельца; ни один прогон не убит молча (stopped_reason в meta.json).
