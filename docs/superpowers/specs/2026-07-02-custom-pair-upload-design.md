## 1. Цель и сценарий пользователя

Сейчас демо работает с одним засеянным документом (RU→EN, 16 абзацев). Пользователь не может принести свой текст. Цель фичи: отдельное окно, где пользователь даёт **свою** пару «оригинал — перевод» (вставкой текста или файлом), явно указывает язык оригинала и язык перевода — и получает полноценный рабочий документ: пер-абзацная оценка по критериям, issues с Accept/Dismiss, re-score, reset к исходной загрузке.

Конкретный проход. Исследователь открывает демо на EMNLP. В верхней панели нажимает «+ Загрузить пару». В модальном окне: в левую панель «Оригинал» перетаскивает файл `kapitel1.docx` — текст извлекается и появляется в поле; в правую панель вставляет свой французский перевод из буфера. Выбирает язык оригинала DE и язык перевода FR в шапках панелей. Жмёт «Далее» — превью выравнивания показывает 7 ↔ 9 абзацев; двумя кликами «⇧ склеить с предыдущим» он сводит перевод к 7. Жмёт «Создать документ» (чекбокс «оценить и прогреть кеш» оставлен включённым). Приложение переключается на новый документ: колонки подписаны «Original (DE)» / «Translation (FR)»; в фоне идёт прогрев — абзацы один за другим получают baseline-оценки и подчёркивания. Он принимает правку — балл пересчитывается. Вкладка Glossary для этого документа пуста (терминологический слой считается офлайн и есть только у засеянного RU→EN документа — честно подписано). Reset возвращает перевод к загруженному состоянию.

## 2. Текущие ограничения (по коду, с доказательствами)

1. **Создания документа нет.** REST-поверхность: `GET /api/documents`, `GET /api/documents/{id}`, `PATCH /api/paragraphs/{pid}`, evaluate/apply-edit/reset, CRUD критериев и моделей, `POST /api/models/{name}/test`, `POST /api/paragraphs/{pid}/terms` — и всё ([app.py:167–640](../../../src/palimpsest/webapp/app.py#L167), список роутов). `POST /api/documents` и `DELETE /api/documents/{id}` отсутствуют. Загрузки файлов (multipart) нигде нет; `python-docx` и `python-multipart` уже резолвятся в `uv.lock` (транзитивно) — прямыми зависимостями их надо будет объявить в `pyproject.toml`.
2. **Схема БД почти готова.** `document` уже содержит `source_lang`, `target_lang`, `version`, `created_at` ([db.py:24–28](../../../src/palimpsest/webapp/db.py#L24)); сид пишет туда `"ru"`, `"en"` ([seed.py:67–71](../../../src/palimpsest/webapp/seed.py#L67)). `paragraph.seed_target` — иммутабельный исходный перевод, к нему откатывает reset ([db.py:31](../../../src/palimpsest/webapp/db.py#L31), [app.py:403](../../../src/palimpsest/webapp/app.py#L403)). Нет только признака «загруженный vs засеянный» документ.
3. **Фронтенд одно-документный.** `store.init()` грузит `summaries[0]` и всё ([store.ts:174–203](../../../frontend/src/demo/store.ts#L174)); переключателя документов в UI нет. DTO уже несёт `sourceLang`/`targetLang` ([api-client.ts:98–110](../../../frontend/src/demo/api-client.ts#L98)), но заголовки колонок захардкожены: «Original (RU)» / «Translation (EN)» ([VariantA.tsx:337–338](../../../frontend/src/demo/variant-a/VariantA.tsx#L337)); то же в шапке таблицы Glossary ([GlossaryTab.tsx](../../../frontend/src/demo/variant-a/GlossaryTab.tsx)).
4. **Судья зашит на RU→EN дважды.** (а) User-сообщение: `f"[SOURCE RU]\n{ru}\n\n[TRANSLATION EN]\n{en}"` ([judge.py:53](../../../src/palimpsest/webapp/judge.py#L53)). (б) Системный промпт читается из файла `prompts/scoring/<id>.md` ([judge.py:42–43](../../../src/palimpsest/webapp/judge.py#L42)), а НЕ из колонки `criterion.prompt` — и все 5 файлов языко-специфичны: accuracy.md начинается с «expert translator … specializing in Russian-English translation»; упоминаний Russian/English: accuracy 8, cultural 12, fluency 18, style 5, terminology 15. Правила внутри тоже RU-специфичные (Runglish, транслитерация кириллицы, цитаты из первоисточников).
5. **Cache-fallback существует только для сид-документа.** `kind='cache'` строки создаёт только сид ([seed.py:5–6](../../../src/palimpsest/webapp/seed.py#L5)). При полном провале live-вызовов `/evaluate` пробует кеш, а если строк нет — возвращает «пустой live-результат, все критерии failed» ([app.py:277–280](../../../src/palimpsest/webapp/app.py#L277), [app.py:317–334](../../../src/palimpsest/webapp/app.py#L317)). Состояние деградации на фронте уже есть: `ParaEvalState.failedCriterionIds` ([store.ts:41–46](../../../frontend/src/demo/store.ts#L41)). Без прогрева загруженный документ живёт **только** в live-режиме.
6. **Терминология — офлайн и RU-специфичная.** Term-строки для сида берутся из офлайн-выхода пайплайна extract→ground→pair ([seed.py:124–147](../../../src/palimpsest/webapp/seed.py#L124)); `POST /api/paragraphs/{pid}/terms` просто читает уже сохранённые строки ([app.py:636–640](../../../src/palimpsest/webapp/app.py#L636)). Live-извлечение есть лишь в Test-пробе модели, и она тоже RU-зашита: промпт «From the Russian paragraph…» ([app.py:517–521](../../../src/palimpsest/webapp/app.py#L517)), стемминг «prefix-4» под русскую морфологию ([app.py:524–530](../../../src/palimpsest/webapp/app.py#L524)), референс — term-строки абзаца idx=1 сид-документа ([app.py:533–543](../../../src/palimpsest/webapp/app.py#L533)). Для произвольной пары языков terms-слой онлайн не производится.
7. **Glossary-вкладка = view поверх term-строк.** Она рендерит `Term[]` из абзацев документа ([GlossaryTab.tsx:1–30](../../../frontend/src/demo/variant-a/GlossaryTab.tsx#L1), [VariantA.tsx:137](../../../frontend/src/demo/variant-a/VariantA.tsx#L137)); эндпоинта `/api/glossary` нет. Для загруженного документа она будет просто пустой — отдельной «поломки» нет, нужен только empty-state.
8. **Бюджет ограждён, но размера документа никто не ограничивает.** Guard: $2 и 200 вызовов на процесс, резервирование до вызова ([budget.py:18–19](../../../src/palimpsest/webapp/budget.py#L18)); таймаут вызова 20 с ([app.py:37](../../../src/palimpsest/webapp/app.py#L37)). `/evaluate` пер-абзацный (≤5 вызовов за клик, [app.py:256–268](../../../src/palimpsest/webapp/app.py#L256)) — стоимость клика ограничена. Но загрузка «войны и мира» без капов убьёт UX (рендер TipTap) и позволит одним документом выесть весь бюджет: 40 абзацев × 5 критериев = 200 вызовов = весь call-cap.
9. **Reset уже совместим с загрузками.** `POST /api/documents/{id}/reset` удаляет только `kind='live'` и восстанавливает `target = seed_target` ([app.py:387–403](../../../src/palimpsest/webapp/app.py#L387)). Если при загрузке писать `seed_target = загруженный перевод`, reset «из коробки» означает «вернуть исходную загрузку». Гонка с live-evaluate уже защищена `version` + in-memory guard (409).
10. **Пересид стирает загрузки.** Сидер дропает файл БД целиком ([db.py:80–91](../../../src/palimpsest/webapp/db.py#L80), [seed.py:1–7](../../../src/palimpsest/webapp/seed.py#L1)). Загруженные документы не переживут `python -m palimpsest.webapp.seed`. Для демо это приемлемо, но надо знать.
11. **У загруженного документа нет baseline.** «Текущий» балл выбирается из `kind IN ('seed','live')`, дельта считается от seed-строк. Без них `aggregateBaseline` = null → UI дельты деградирует до «—». Прогрев (§5.6) закрывает и это: первый оплаченный проход пишется как baseline.

## 3. Варианты архитектуры (история выбора)

### Вариант 1 — минимальная модалка «вставь два текста» (S)

Одно-шаговая модалка: два textarea, два селектора языка, заголовок. Сервер сам режет оба текста по пустым строкам (`\n\s*\n`); при несовпадении числа абзацев — `422` с `{sourceCount, targetCount}`, пользователь чинит пустые строки руками в textarea.

- Плюсы: минимум поверхности, всё серверное поведение тривиально тестируется.
- Минусы: несовпадение разбивки — частый случай (переводчики склеивают/режут абзацы), а чинить его вслепую по счётчику мучительно. На сцене это выглядит как отказ.
- Оценка: **S** (~0.5–1 день).

### Вариант 2 — модалка с превью выравнивания (M) — ✅ утверждён владельцем

Двух-шаговая модалка. Шаг 1 — тексты (вставка или файл) + языки + заголовок. Шаг 2 — превью: таблица пар «source ↔ target» со счётчиками; лишние абзацы подсвечены; у ячеек кнопка «⇧ склеить с предыдущим» (клиентская операция). «Создать документ» активна только при равном числе непустых пар. На сервер уходит уже выровненный список пар — сервер только валидирует и вставляет.

- Плюсы: типовая проблема выравнивания решается на глазах у пользователя за 2–3 клика; сервер остаётся тупым и надёжным; путь отступления — выкинуть кнопки склейки и оставить read-only превью со счётчиками без изменения контракта.
- Минусы: +1 экран UI; merge-кнопки надо аккуратно протестировать.
- Оценка: **M**; с расширениями rev-2 (файлы + прогрев) — **M+** (~3–4 дня с тестами).

### Вариант 3 — файлы с авто-выравниванием, живая терминология (L) — отклонён

Авто-выравнивание эмбеддингами (LaBSE/Bertalign), онлайн-терминология для произвольных пар. Исследовательские задачи, а не фичи; 1.5–2 недели; до 10 июля не успевает. Отклонён. Файловый ввод из этого варианта перенесён в скоуп варианта 2 (без авто-выравнивания: файл → чистый текст → то же превью шага 2).

## 5. Контракты утверждённого варианта

### 5.1 API

**`POST /api/documents`** — создать пользовательский документ.

```
Body (application/json):
{
  "title": "Der Zauberberg — ch. 1",       // 1..120 символов
  "sourceLang": "de",                        // ISO 639-1, нижний регистр
  "targetLang": "fr",                        // ISO 639-1, != sourceLang
  "precompute": true,                        // прогрев после создания (default true), §5.6
  "paragraphs": [                            // 1..40 элементов
    { "source": "…", "target": "…" }         // обе строки непустые, каждая ≤ 4000 символов
  ]
}
Ответы:
  201 → полный Document DTO (как GET /api/documents/{id})
  422 → { "error": "...", код в detail }:
        empty_paragraphs | empty_cell (с index) | same_language |
        too_many_paragraphs (лимит 40) | paragraph_too_long (index, лимит 4000) |
        bad_lang_code | title_required
  413 → тело > 1 МБ (стандартный лимит)
```

Семантика вставки: `document(origin='upload', source_model='user', seed_model=NULL, seed_prompt_variant=NULL, version=0)`; для каждой пары `paragraph(source, target, seed_target=target)`. Score/issue/term строки при вставке не создаются; при `precompute=true` их асинхронно допишет прогрев (§5.6). Endpoint публичный (решение владельца №1).

**`POST /api/documents/extract-text`** — извлечь чистый текст из .docx (единственный формат, который ходит на сервер, см. §5.4).

```
Запрос: multipart/form-data, поле "file"
Принимается: .docx (MIME application/vnd.openxmlformats-officedocument.wordprocessingml.document)
Лимит: 5 МБ
Ответы:
  200 → { "text": "…", "nParagraphs": 12 }   // абзацы через \n\n, пустые выброшены
  415 → { detail: "unsupported_type" }        // не .docx; старый .doc — отдельная подсказка
                                              // «Сохраните как .docx и загрузите снова»
  422 → { detail: "unparseable_file" }        // битый zip / не wordprocessingml
  413 → файл > 5 МБ
```

Сервер: `python-docx`, абзацы из `document.paragraphs` (родные границы абзацев из XML — лучше эвристики пустых строк), пустые отбрасываются. Текст таблиц, колонтитулов и картинок **не извлекается** (ограничение `doc.paragraphs`; вне скоупа по решению №6, §4). Эндпоинт stateless: ничего не пишет в БД, только конвертирует. Требует объявить `python-docx` и `python-multipart` прямыми зависимостями в `pyproject.toml` (в `uv.lock` уже есть).

**`DELETE /api/documents/{doc_id}`** — удалить пользовательский документ.

```
  204 → удалён; каскад paragraph/score/issue/term обеспечивает ON DELETE CASCADE в DDL (§5.2);
        бегущий прогрев останавливается
  409 → { "error": "seed_document" }        // origin='seed', сид-документ удалить нельзя
  409 → { "error": "evaluate_in_flight" }   // незавершённый /evaluate (тот же _evaluating guard, что у reset)
  404 → нет такого документа
```

Важно (решение №8, CRITICAL из `/verify-spec`): в текущем DDL нет `ON DELETE CASCADE`, а `PRAGMA foreign_keys=ON` включён ([db.py:22](../../../src/palimpsest/webapp/db.py#L22), [db.py:76](../../../src/palimpsest/webapp/db.py#L76)) — «наивный» DELETE документа упал бы в `sqlite3.IntegrityError` → 409 через существующий exception-handler ([app.py:32–34](../../../src/palimpsest/webapp/app.py#L32)), и фича была бы мертва. Поэтому каскад закрепляется на уровне схемы (§5.2); хендлеру остаются только пре-чеки 409 выше.

Существующие эндпоинты не меняют форму. `POST /api/documents/{id}/reset` для загрузки уже означает «вернуть исходный перевод» (см. §2 п.9) — изменений не требует.

**Дельта DTO.** `GET /api/documents[/{id}]` дополнительно отдаёт `origin: "seed"|"upload"` (фронту — прятать Delete у сида) и, для загрузок с бегущим/завершённым прогревом, `precompute: {"status": "running"|"done"|"stopped"|"skipped", "done": k, "planned": m}` (in-memory, после рестарта сервера отсутствует). `EvaluateResponse` получает поле `aggregatePrev: number | null` — последний замороженный агрегат абзаца среди `kind IN ('seed','live')` **до** вставки строк этой оценки; `null` = это самая первая оценка абзаца. Нужно для правила дельты (решение №7, §5.5): `aggregateBaseline` его не покрывает — у загрузки без прогрева seed-строк нет вообще, и дельта «старый live → новый live» без `aggregatePrev` невыводима на сервере.

Хук вычисления `aggregatePrev` — уже существующий пре-insert вызов `_para_score_views` в `evaluate()` ([app.py:284](../../../src/palimpsest/webapp/app.py#L284)): сейчас `latest, _, _, _, _ = …` отбрасывает агрегат — захватываем четвёртый элемент (`agg`) как `aggregatePrev`. И критично (находка F4): `_cache_response` — отдельный dict-литерал ([app.py:317–334](../../../src/palimpsest/webapp/app.py#L317)) — обязан **тоже** отдавать `aggregatePrev`: значение выводится из его вызова `_para_score_views` ([app.py:323](../../../src/palimpsest/webapp/app.py#L323)), который выбирает только `kind IN ('seed','live')` — то есть **не зависит от cache-значений этого ответа** (порядок чтения cache-строк не важен). Иначе дельта-бейдж молча подавлялся бы при каждом cache-фолбэке.

### 5.4 Файловый ввод: контракт извлечения текста

Принцип: **textarea — единственный источник правды.** Файл любым способом (кнопка или drag-and-drop) превращается в чистый текст и **заполняет textarea своей стороны**; дальше вставка и файл неразличимы — одна валидация, один шаг 2, один `POST /api/documents`. Извлечённый текст можно править руками до «Далее».

Разделение клиент/сервер — гибрид:

| Формат | Где | Как | Почему |
|---|---|---|---|
| .txt | клиент | `FileReader` → `TextDecoder('utf-8')`; если в результате есть U+FFFD — повторная декодировка `windows-1251` (частый случай для старых RU-текстов); если и там мусор — вставить как есть + warning-toast | Тривиально, без сети, мгновенно |
| .md | клиент | Та же декодировка → снятие разметки (~40-строчная функция, юнит-тесты): маркеры заголовков `#`, эмфазис `*_`, инлайн-код и маркеры код-фенсов (содержимое остаётся), `[текст](url)` → текст, картинки `![…]` — выбрасываются, HTML-теги — выбрасываются, маркеры цитат `>`, `---` — выбрасываются, строки таблиц → ячейки через « — » | Владелец просил «чистый текст» — снимаем разметку; логика простая и детерминированная |
| .docx | сервер | `POST /api/documents/extract-text` (§5.1); на время запроса панель в busy-состоянии | Бинарный zip-формат; `python-docx` — зрелый парсер, уже в lock-файле; серверный код покрывается pytest (тестовая культура проекта), фронтенд-бандл не растёт |

Отвергнутые альтернативы: (а) «всё на сервере» — multipart ради текстовых файлов, лишний round-trip и поверхность; (б) «всё на клиенте» (mammoth.js для .docx) — ноль изменений бекенда, но +тяжёлая JS-зависимость в бандл и парсер послабее python-docx; тестировать пришлось бы в браузере.

Правила заполнения: файл **заменяет** содержимое textarea; если оно непустое — confirm «Заменить вставленный текст содержимым файла?». Скрытый `<input type="file" accept=".docx,.md,.txt">`; drag-and-drop на textarea — тот же путь. После заполнения работают обычные проверки шага 1 (≤40 абзацев, ≤4000 символов на абзац) — независимо от происхождения текста.

Решения компоновки и почему так:

- **Две симметричные панели, каждая самодостаточна.** Всё, что относится к стороне, живёт внутри её рамки: подпись роли + селектор языка в шапке, textarea в центре, кнопка файла + счётчики в подвале. Селектор языка в шапке панели визуально привязывает язык к стороне — нельзя перепутать, «чей» это язык.
- **Вставка — первичный путь.** Textarea доминирует по площади; placeholder называет оба способа. Вставка — ноль кликов, самый быстрый путь на демо.
- **Кнопка «Загрузить файл» — вторичная, по одной на панель, в подвале своей панели.** Никакой глобальной кнопки загрузки: с ней возник бы вопрос «в какую сторону лёг файл». Пер-панельная кнопка снимает двусмысленность полностью; drag-and-drop на textarea — эквивалент.
- **Файл наполняет textarea** (см. §5.4) — после загрузки пользователь видит и может править ровно тот текст, который уйдёт дальше. Смешанный сценарий (слева файл, справа вставка) работает сам собой.
- **Busy-состояние для .docx:** на время `extract-text` textarea панели затемняется спиннером «Извлекаем текст…», кнопки панели неактивны. Ошибка — красная строка в подвале панели, textarea не трогается; тексты фиксированы (находка M5): 415 → «Формат не поддерживается. Сохраните документ как .docx и загрузите снова»; 422 `unparseable_file` → «Файл повреждён или не является документом Word (.docx)»; 413 → «Файл больше 5 МБ — разбейте документ или вставьте текст частями».
- **Живые счётчики** «N § · M симв.» в подвале (клиентский сплит по `\n\s*\n`) — пользователь ещё до шага 2 видит, что 7 ≠ 9. В первозданном состоянии счётчик **виден** и показывает «0 § · 0 симв.» (не прячется) — находка M6.
- **Валидация шага 1:** «Далее» активна, когда оба текста непустые, языки различаются, ≤40 абзацев и ≤4000 символов на абзац с каждой стороны. Во всех остальных случаях чип показывает **только балл**: ни «+8.1», ни стрелки от нуля/null. Прогрев считается первой оценкой: его строки приходят через refetch документа, там `aggregate == aggregateBaseline` (baseline и есть прогрев) → бейдж скрыт статическим правилом сам собой. Первая live-оценка после прогрева даёт `aggregatePrev` = балл прогрева → бейдж «старый → новый» появляется, как и требует владелец. Для сид-документа поведение не меняется: его baseline существует с сида, дельта против baseline — это и есть «старый → новый». ### 5.6 Прогрев кеша (precompute)

**Когда.** Fire-and-forget: `POST /api/documents` с `precompute=true` (чекбокс шага 2, default ON) отвечает 201 сразу, затем `asyncio.create_task(_precompute(doc_id))`. Синхронный вариант с прогресс-баром отвергнут: 12 абзацев × до 20 с таймаута ([app.py:37](../../../src/palimpsest/webapp/app.py#L37)) — минуты ожидания на сцене; отдельная кнопка «Прогреть» отвергнута — владелец явно просил прогрев в момент загрузки, а фоновый бейдж «прогрев 5/12 §» даёт ту же прозрачность без лишнего клика. Если документ создан с `precompute=false`, статус присутствует в DTO **явно**: `{"status": "skipped", "done": 0, "planned": 0}` — поле не опускается.

**Что пишет.** Один оплаченный судейский проход на абзац (все enabled-критерии), из его результата — **две** записи:
- `kind='seed'` — честный baseline: score-строки + issue-строки (`status='open'`). Это чинит §2 п.11 (дельта у загрузок) и даёт «из коробки» подчёркивания — загруженный документ выглядит как сид-документ, только с настоящими, не постановочными данными.
- `kind='cache'` — копии score-строк **с теми же значениями** (без искусственного uplift'а сида, [seed.py:31](../../../src/palimpsest/webapp/seed.py#L31)) — сценический fallback для `_cache_response` ([app.py:317–334](../../../src/palimpsest/webapp/app.py#L317)). Issue-строки в cache не дублируются: as built, cache-фолбэк возвращает только скоры.

`criteria_key` штампуется на момент прогрева — так же, как это делают сид и `/evaluate`. Запись **поатомно на абзац**: если хотя бы один критерий абзаца провалился — строки этого абзаца не пишутся вовсе (иначе замороженный `aggregate` врал бы, а `_cache_response` рассчитывает на полный набор критериев, [app.py:330–331](../../../src/palimpsest/webapp/app.py#L330)). Частичное покрытие документа — норма: fallback пер-абзацный, непокрытые абзацы живут live-only, как без прогрева.

**Прогрев = первая оценка (решение №7).** После прогрева абзац показывает установленный балл **без дельта-бейджа** (правило §5.5: `aggregate == aggregateBaseline` → бейдж скрыт). Дельта появляется только со второй оценки — первой live-оценки поверх прогрева (`aggregatePrev` = балл прогрева → бейдж «старый → новый»). Никакого постановочного uplift'а у загрузок нет ни в baseline, ни в cache.

**Сколько стоит и как ограждено.** Реальная статистика (`budget_calls.jsonl`, 11 вызовов): средний вызов $0.0036, максимум $0.0106. Прогрев покрывает **первые `min(N, 12)` абзацев** × 5 критериев = ≤60 вызовов ≈ **$0.22 типично, ≤$0.65 в худшем случае**. Почему «первые 12», а не весь документ и не меньший кап загрузки: кап 40 абзацев — про размер документа и UX, его не трогаем; 40×5=200 вызовов = весь call-cap ([budget.py:19](../../../src/palimpsest/webapp/budget.py#L19)) — прогревать всё нельзя; 12 абзацев — это ~2 экрана демо-прокрутки, сценическое взаимодействие живёт в начале документа. Ограждения:
- каждый вызов идёт через тот же `budget.reserve()/settle()` (глобальные $2/200 держат);
- отдельный глобальный суб-кап прогрева: env `PALIMPSEST_PRECOMPUTE_CALLS` (default 80 ≈ $0.3 типично) на процесс, суммарно по всем загрузкам — публичный endpoint не может выесть бюджет живого демо прогревами. Счётчик суб-капа проверяется И инкрементится **до** каждого вызова под тем же `asyncio.Lock`, что и `budget.reserve()` (решение №10: переиспользуем лок и состояние budget, вторую схему блокировок не заводим). Как и счётчики budget, суб-кап **обнуляется при рестарте процесса** — тот же принятый класс риска (L4);
- лог: `budget.log_call(..., endpoint="precompute")` — расход виден в `budget_calls.jsonl`.

**Порядок и гонки.**
- Абзацы прогреваются **последовательно** (не gather всех сразу): нет всплеска из 60 конкурентных вызовов, деградация при исчерпании бюджета аккуратная.
- Прогрев **не** держит `_evaluating` guard (иначе reset был бы заблокирован минутами). Пропуск уже оценённых абзацев проверяется **дважды** (решение №9, закрывает TOCTOU-гонку): дешёвый чек до LLM-вызовов (не тратить деньги зря) и обязательный **повторный чек внутри критической секции `db._lock` непосредственно перед вставкой**. LLM-вызовы абзаца длятся до ~20 с — за это окно live-`/evaluate` мог записать свои строки; если при повторном чеке строки появились, судейские результаты абзаца **выбрасываются без записи**. Без повторного чека прогрев вставил бы `kind='seed'` с более поздним `created_at`, и `_para_score_views` (выборка «текущего» по `created_at DESC`, [app.py:101](../../../src/palimpsest/webapp/app.py#L101)) молча перекрыл бы live-балл пользователя. У пропущенного абзаца не будет cache-фолбэка — приемлемо.
- Запись абзаца (находка M3): решение «писать/пропустить» принимается в памяти **до** первой вставки; все строки абзаца (seed-скоры + cache-скоры + issue-строки) вставляются под `db._lock` одним блоком с **единственным commit на границе абзаца** — зеркально паттерну записи `/evaluate` ([app.py:282–303](../../../src/palimpsest/webapp/app.py#L282)). Падение процесса между LLM-вызовами и записью не оставляет ни одной частичной строки: до commit результаты живут только в памяти.
- `BudgetExceeded` или исчерпание суб-капа → прогрев останавливается целиком, `status='stopped'`.
- Документ удалён во время прогрева → задача тихо завершается (проверка существования перед каждым абзацем).
- Reset во время/после прогрева безопасен: reset **архивирует** `kind='live'` (→ `kind='archived'`/`status='archived'`, сохранность предсказаний wave-4, `reset_document` в app.py) — baseline и cache переживают; активные вьюхи возвращают документ ровно в «свежезагруженное + прогретое» состояние, а архивные строки остаются в БД.
- Рестарт сервера → фоновая задача и in-memory статус теряются, уже записанные строки остаются; возобновления нет (одноразовая задача, не очередь). Первая live-оценка абзаца, пропущенного прогревом, — его первая оценка вообще: `aggregatePrev = null` → без дельты (правило §5.5).

### 5.7 Edge cases

| Кейс | Поведение |
|---|---|
| Разное число абзацев | Шаг 2 блокирует «Создать документ», подсвечивает сирот, чинится merge-кнопками; сервер дублирует проверку только на непустоту пар (выравнивание — ответственность клиента по контракту) |
| Огромный документ | Клиент: блок на шаге 1 (>40 абзацев / >4000 символов в абзаце); сервер: 422 `too_many_paragraphs` / `paragraph_too_long`, 413 на тело >1 МБ |
| Пустой перевод (весь или ячейка) | Шаг 1: «Далее» неактивна при пустом textarea; шаг 2: пустая ячейка = сирота; сервер: 422 `empty_cell` с index |
| Один и тот же язык дважды | UI блокирует «Далее» с подсказкой; сервер 422 `same_language` |
| Текст одним куском без пустых строк | Валидно: 1 абзац (если ≤4000 символов), превью покажет одну пару |
| Файл .doc (старый бинарный формат) | 415 c подсказкой «Сохраните как .docx и загрузите снова» — python-docx его не читает; честнее отказать сразу |
| .txt/.md не в UTF-8 | Клиентский retry `windows-1251` при U+FFFD; если и после — мусор, текст вставляется + warning «проверьте кодировку файла» |
| .docx с таблицами/колонтитулами | Текст таблиц и колонтитулов не извлекается (`doc.paragraphs`) — вне скоупа по решению №6 (§4) |
| Файл > 5 МБ | 413 из `extract-text`; клиент проверяет `file.size` до отправки и показывает ошибку локально |
| Drag-and-drop нескольких файлов | Берётся первый, warning «загружен только первый файл» |
| Извлечённый текст превышает капы | Обычная валидация шага 1 по содержимому textarea (SSOT) — файл не обходит лимиты |
| RTL-языки (ar) | `dir="auto"` на контейнерах текста абзаца в обеих колонках и в превью шага 2 |
| Reset загруженного документа | Работает без изменений: `target ← seed_target`, live-строки удаляются; baseline+cache прогрева переживают ([app.py:387–403](../../../src/palimpsest/webapp/app.py#L387)) |
| Провал `/evaluate` на непрогретом абзаце | `failedCriterionIds` + toast; баллы не появляются, документ не портится (append-only) |
| Evaluate непокрытого прогревом абзаца, все судьи упали | Ответ несёт `aggregatePrev: null` (то же правило первой оценки, находка M8) + полный `failedCriterionIds` — дельта-бейдж не рендерится |
| Cache-фолбэк (сид-документ или прогретая загрузка) | `_cache_response` тоже отдаёт `aggregatePrev` — значение выводится из `_para_score_views` (только seed/live) и не зависит от cache-значений ответа (§5.1, находка F4); иначе бейдж молча подавлялся бы при каждом фолбэке |
| Исчерпан бюджет | `BudgetExceeded` = провал критерия ([app.py:235](../../../src/palimpsest/webapp/app.py#L235)) → тот же путь, что провал сети; бегущий прогрев останавливается со статусом `stopped` |
| Live-evaluate во время прогрева | Оба пути append-only; прогрев пропускает абзацы, уже имеющие score-строки — двойной траты нет |
| Самая первая оценка абзаца (прогрев или live) | Чип показывает только балл, без дельта-бейджа (`aggregatePrev == null` / `aggregate == aggregateBaseline`) — решение №7, правило в §5.5 |
| Пересид БД | Загрузки стираются (сидер дропает файл БД) — фиксируем как известное поведение демо |
| Test-проба моделей | Не трогаем: она по-прежнему referencing сид-абзац idx=1 ([app.py:533–543](../../../src/palimpsest/webapp/app.py#L533)) и не зависит от загрузок |
