```python
for r in conn.execute("SELECT * FROM issue WHERE paragraph_id=? ORDER BY id", (pid,)):
    if r["status"] in ("accepted", "dismissed", "outdated"):
        out.append(r)                                      # history
    elif r["status"] == "open" and r["criterion_id"] in live_crits and r["kind"] == "live":
        out.append(r)                                      # live open set
    elif r["status"] == "open" and r["kind"] == "seed":
        out.append(r)                                      # seed open set
    # superseded / archived → dropped, never reach the API
```

- **Пере-сид baseline** для устранения gap 8.3↔7.2 — требует денег И снёс бы предсказания (конфликт с инвариантом). Смягчение — seed-param (Б6) + criteria_key-бейдж (Б3.6). Полноценный пере-сид — отдельное решение владельца.
- **Soft-delete документов** (`DELETE /api/documents/{id}`) — загрузки одноразовы (known_issues); архивирование их предсказаний — кандидат в wave-5.
- **Matcher parity** (клиент indexOf vs сервер whitespace-tolerant), **дубликаты фрагментов** (все подчёркнуты, заменяется первый), **stale-флаг после reload**, **персист бюджет-счётчиков** — кандидаты в wave-5, в known_issues.

## Порядок исполнения (субагент-driven, sonnet, последовательно во избежание конфликтов файлов)

app.py делят Б3+Б5; seed.py — Б3+Б4; judge.py — Б2+Б6; variant-a.css — Б1+Б5 → параллельный запуск по блокам небезопасен в общем worktree. Порядок: **Б5 → Б1 → Б3 → Б4 → Б2 → Б6**. Между блоками — прогон затронутых тестов (агент сам гоняет и отчитывается; оркестратор проверяет отчёт и при зелёном идёт дальше). Коммиты: по одному на блок, КРОМЕ Б5 (3 коммита: backend/frontend/docs). Conventional Commits, без Co-Authored-By.

⚠️ **verify-spec — line-drift (важно):** Б5 удаляет ~15 строк ВЫШЕ строки 156 в app.py (import hmac :9, ADMIN_TOKEN :50, `_require_admin` :64-68, admin/check :213-218) → все абсолютные номера строк Б3 в app.py сдвинутся к моменту его запуска. **Каждый исполнитель обязан заново grep'ать целевую строку/паттерн в ТЕКУЩЕМ файле, а не доверять номерам из спеки.** Все анкеры Б3 (и css/seed.py-анкеры) даны как строки-паттерны для поиска: `DELETE FROM issue WHERE paragraph_id=? AND criterion_id=? AND kind='live' AND status='open'`, `DELETE FROM score WHERE paragraph_id=? AND kind='live'`, тело `_para_issues`, селекторы `.va-term-dot`/`.va-unlock-row`. Номера строк — только ориентир.

## Критерии успеха волны

1. Все 5 правок владельца видимы и работают в браузере (e2e).
2. Инвариант сохранности: grep по webapp — ноль `DELETE FROM score`/`DELETE FROM issue` на пользовательских путях (остаётся только каскад при удалении документа-загрузки, вне скоупа).
3. База тестов не деградировала: pytest ≥ прежнего (минус удалённые admin-тесты, плюс новые), vitest, tsc clean.
4. UI English-only; owner-facing отчёт — русский, dark HTML, served.
5. Prod-ops runbook готов и отдан владельцу.
