## 1. Концепция и скоуп ✅

Демка про **интерпретируемость оценки перевода** исторических текстов со сложной терминологией. Ценность — *понятно, почему перевод хорош/плох*, и ошибки исправляемы.

- **Вход:** оригинал + предлагаемый перевод. **Атомарная единица:** 1 абзац (выровнены 1:1).
- **Любая пара языков**, произвольные LLM по API-ключу.
- **Три контрибьюшена:** (1) детерминированная адаптация терминологии (Wikidata+Wikipedia, не LLM); (2) интерпретируемый анализ ошибок по кастомным критериям (LLM-as-judge, Grammarly-стиль); (3) end-to-end улучшение (оценили → приняли правки → качество выросло).
- **Бьём:** у обычных метрик нет интерпретируемости; LLM сам по себе плохо тянет сложную терминологию.

## 3. Хрома и навигация ✅ (переработано)

Два уровня навигации, **оба взяты из обоснованных источников, не выдуманы** (см. §11):

**(а) Верхняя навигация приложения — лёгкие вкладки-секции** (не тяжёлый ribbon, как в CAT-тулах, а их облегчённая форма): `Документ · Глоссарий · Ранжирование · Настройки`.

**(б) Внутри «Документ» — фильтр оценщиков с МНОЖЕСТВЕННЫМ выбором** (не взаимоисключающие плашки!): можно включить несколько оценщиков сразу и видеть их правки одновременно, цветом по оценщику. Это модель «категорий правок» Grammarly / типологии Thresh.

```
┌ Palimpsest │ [Документ · Глоссарий · Ранжирование · Настройки] │ общий 7.8 ─────────┐
├ оценщики (мультивыбор): [✓Точность][✓Беглость][ Стиль][✓Культ.адапт]… [✓Термины KG] ┤
├───────────────┬────────────────────────────┬──────────────────────────────────────┤
│ Оригинал RU   │ Перевод EN                 │ Замечания ВСЕХ выбранных оценщиков,    │
│ (только чтение)│ (правки всех выбранных,    │ цветные по оценщику; заголовок         │
│               │  цветные подчёркивания)    │ карточки = «оценщик · модель»          │
└───────────────┴────────────────────────────┴──────────────────────────────────────┘
```

- У каждого оценщика свой цвет → и подчёркивание в тексте, и карточка, и (позже) бейдж скора одного цвета.
- «Термины (KG)» — тоже элемент фильтра, но отдельного типа (детерминированная подсветка, см. §5).
- Скор каждого абзаца — ❓ §10.

## 4. Контрибьюшен #2 — LLM-судьи ✅

**Оценщик = настраиваемый объект, элемент фильтра:**

```
EvaluatorConfig = {
  id, label, color,
  model, api_key, base_url,
  prompt,                       # включает описание шкалы
  scale: { min: float, max: float, labels?: [...] },   # 1–100 | 1–5 | 1–3 (critical/major/minor) | …
  weight: float
}
```

- Пользователь задаёт **имя · модель · промпт (со шкалой) · ключ**. Терминологию как отдельный LLM-критерий **не хардкодим** — рубрики кастомные, а каноническую терминологию ведёт KG-слой (§5).
- **Шкала — произвольный float**, часть конфига оценщика (1–100 / 1–5 / 1–3). UI рисует бейдж/цвет из `scale`; никакого зашитого 1–10.
- **Имя модели — в заголовке карточки** (`оценщик · модель`). ✅
- **Дефолтные оценщики — `prompts/03_scoring/v2`** (компактнее v1): Точность, Беглость, Стиль, Культ. адаптация (терминологию убрали в KG). Это просто пресет — пользователь меняет/добавляет.
- **Выход (Grammarly-стиль):** спан → объяснение → правка. Accept применяет (TipTap-transform / `04_correction`), Dismiss убирает.
- **Канонический формат вывода — MQM** (5 классов × 3 severity; verbatim-span валидируется бэком) → сопоставимость с прайор-арт + «качество на MQM» для статьи. 🟡
- **Скоры — двухуровневый контракт:** бэк отдаёт per-paragraph `{paragraph_id, evaluator_id, score:float, spans[]}`; агрегат считает фронт.

### Настройка оценщиков ✅
- Управление набором — секция **«Настройки»** (список оценщиков: добавить/удалить/цвет/порядок).
- Быстрое редактирование одного — **drawer** (промпт во всю высоту, строка `модель·ключ·t·base·✎`, футер `→ score + span-правки · вес · Прогнать`), открывается из ⚙ на чипе оценщика.

## 5. Контрибьюшен #1 — терминология (KG-слой) ✅

Детерминированная адаптация через **Wikidata + Wikipedia** (не LLM).

- **Делаем только ОДИН сигнал — точность пары оригинал↔перевод:** подчёркиваем пару 🟢/🟡/🔴 по тому, совпал ли перевод с каноном по тому же смыслу (langlinks → каноническая форма). *(Сигнал «сложность исходного термина» — отложен, чтобы не перегружать; future work.)*
- Элемент фильтра «Термины (KG)»; инлайн — только цвет, детали (вердикт + канон + кандидаты) в термпанели/тултипе; double-click — вставка канона.
- **Differentiating-фича** для статьи (прайор-арт KG-MT/XC-Translate: GPT-4 ≈35% m-ETA на именах).
- ⚠️ **Любая пара языков** (§1) → KG-матчинг **нельзя оставлять русско-привязанным** (pymorphy3, world-history-таблицы). Нужен языко-агностичный матчинг (мультиязычные метки Wikidata + поверхностные формы; морфология опционально по языку). См. §10.

## 6. Контрибьюшен #3 — end-to-end улучшение ✅

Загрузил оригинал → сгенерировал перевод LLM **или** загрузил готовый → прогнал оценщиков (критерии + KG-термины) → принял правки → **повторная оценка показывает рост качества**. Эффект «до/после» — ядро демо-нарратива.

## 7. Контракт данных (эскиз)

- **per-paragraph × per-evaluator:** `{ paragraph_id, evaluator_id, score:float, scale:{min,max,labels?}, spans:[{start,len,class,severity,explanation,suggestion}] }`.
- **термины:** `{ paragraph_id, source_span, target_span, pair_accuracy:🟢🟡🔴, canonical, qid, candidates[] }`.
- Sentinel: `null` = терминальный skip, `-1` = ретраибельный parse-fail. Спаны — символьные offset’ы.

## 13. Реализовано — as-built Variant A (собрано и проверено 2026-06-30)

Выбран и собран **Variant A «Reader»** (оригинал слева, перевод справа). Variant B «Workbench» — ⚠️ **LEGACY, удалён 2026-07-02** (см. выше). Код — `web-prototype/src/demo/variant-a/`, общий слой данных — `src/demo/data.ts` (реальные данные пилота: абзацы 15/27/64/275, 20 замечаний по 5 критериям, 8 термопар).

- **Взаимодействие.** Абзац — выделяемая единица с мелкой нумерацией §N. Оригинал (RU) read-only, кликабелен (клик выделяет); перевод (EN) — редактируемый TipTap (фокус тоже выделяет). Инспектор справа с переключателем **Issues / Scores**, сфокусирован на выбранном абзаце; **«Accept all»** на абзац + док-уровневый «Accept all»; клик по строке **Ranking** → переход к абзацу и фокус инспектора.
- **Оценщики = критерии** (Accuracy, Fluency, Style, Cultural Adaptation, Terminology). Шкала **фиксированная 1–10 + вес → итог как взвешенная сумма**. Дефолтные промпты — `prompts/03_scoring/v2`, рендерятся как **markdown (скроллятся)** в Settings.
- **Model Registry** (Settings, отдельная секция): в критерии модель выбирается **только по имени**; все параметры (provider, modelId, baseUrl, apiKey, temperature, maxTokens) — в реестре, предзаполнен моделями OpenRouter.
- **Терминология — два механизма** (закрывает §5): (1) обычный LLM-критерий «Terminology»; (2) **KG-разметка пар** — термин подсвечен инлайн **с обеих сторон** (RU `sourceTerm` ↔ EN `targetTerm`), точка вердикта 🟢🟡🔴 + значок-номер пары, **ховер подсвечивает пару напротив**; полный список — вкладка **Glossary**.
- **Цвета критериев** — холодная палитра без зелёного/жёлтого/красного: Accuracy `#4d8dff`, Fluency `#18c0d9`, Style `#c77dff`, Cultural Adaptation `#ff66c4`, Terminology `#8a8cff`. 🟢🟡🔴 закреплены **только** за вердиктом терминологии.
- **Скор абзаца** — чип общего скора у правого поля. При Accept/«Accept all» — **асинхронный ре-скоринг** (имитация долгого вызова LLM-судьи): чип/полосы/док-скор показывают «обновляется» (спиннер+шиммер ~0.7–1.2с, кнопки Accept заблокированы), затем значение растёт с зелёной **▲-дельтой**. Это контрибьюшен #3 «до/после» (общий скор 8.4 → 9 при принятии всех правок).
- **Наложения критериев** — слоёные подчёркивания (стиль B): на пересечении спанов параллельные цветные линии (реальные кейсы: Accuracy⊃Terminology «bearers of revenue»; Accuracy+Cultural «regardless of his formal legal status»; Accuracy+Terminology «the Persian fleet»).

**Контракт данных `TermPair`** (точка интеграции с бэкенд-моделью извлечения терминов):
`{ id, paragraph (pilot-id), sourceTerm (verbatim substring RU), targetTerm (verbatim substring EN), verdict 🟢🟡🔴, canonical, candidates[], note }`. Инвариант: `sourceTerm`/`targetTerm` — **точные подстроки** `source`/`translated` абзаца (фронт ищет через `indexOf`). Бэкенд-модель отдаёт `term_pairs.json` по этой схеме; фронт заменяет ею моки в `data.ts`.

**Баг, найден и исправлен.** Первая сборка падала в рантайме: терминология инжектилась прямо в DOM редактора TipTap → мутация → событие `update` → бесконечный цикл (чёрный экран). Переписано на **ProseMirror-декорации** (как подчёркивания) + делегирование ховера/клика — цикла нет.

**Проверено вживую** (скриншоты `_screenshots_staging/merged-A-*.png`): консоль чистая; все 4 вкладки и переходы; парность терминов (ховер подсвечивает пару с обеих сторон); ре-скоринг (loading → ▲, 8.4→9); Ranking-прыжок. Авто-тестами не покрыто (прототип-песочница).
