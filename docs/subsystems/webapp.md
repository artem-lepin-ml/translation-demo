## Purpose

Interactive web application for human evaluation of machine-translated paragraphs.
A user reads source Russian text alongside an editable English translation, reviews
LLM-generated issues, accepts or dismisses suggestions, and watches quality scores
update in real time. The goal is a compelling demo of the Palimpsest evaluation loop
for academic and industry audiences.

## Architecture

### Backend (`src/palimpsest/webapp/`)

| Module | Responsibility |
|---|---|
| [`app.py`](../../src/palimpsest/webapp/app.py) | FastAPI entry point. Defines all HTTP routes, serialization helpers, and the async `/evaluate` loop. Orchestrates `db`, `aggregate`, and `judge`; enforces append-only score writes and the cache-fallback protocol. |
| [`db.py`](../../src/palimpsest/webapp/db.py) | SQLite persistence. Single shared connection, threading lock, schema constant `SCHEMA`, `connect()`, `init_db()`. All writes in `app.py` are serialized through `db._lock`. |
| [`aggregate.py`](../../src/palimpsest/webapp/aggregate.py) | Computes a single 0–10 aggregate from per-criterion values. Each criterion is normalized to its own `[scaleMin, scaleMax]` before weighted averaging. Used identically by seed and `/evaluate` so baseline and latest are always comparable. |
| [`judge.py`](../../src/palimpsest/webapp/judge.py) | LLM-as-judge for a single criterion. Reads `prompts/scoring/<id>.md`, calls `LLMClient.complete()`, parses JSON (strips fences tolerantly, drops trailing commas before `}`/`]`, else falls back to the outermost `{...}` — see `_parse_json` and [known_issues.md](../known_issues.md)), returns `{value, summary, issues}` with camelCase wire shapes. `judge_one`/`scoring_system_prompt` take `source_lang`/`target_lang` (ISO code or free-text name — `lang_name` maps the 12 known codes to full names and passes anything else through as typed): every scoring prompt is prefixed with "You are evaluating a translation from {X} into {Y}." — including `(ru, en)`, which used to be byte-for-byte. Any pair other than Russian→English also gets a one-line adapter preamble ("This rubric was written for Russian→English…"); the user message labels source/translation with full language names (`[SOURCE — German]`/`[TRANSLATION — French]`). |
| [`seed.py`](../../src/palimpsest/webapp/seed.py) | One-shot DB seeder. Drops and recreates the schema, inserts the default model, four criteria (Cultural Adaptation dropped wave-4), one document, 15 paragraphs (rebuilt by [seed-refresh](../superpowers/plans/2026-07-02-seed-refresh.md)) with `kind='seed'` baseline scores/issues, `kind='cache'` uplift scores, mock terms, and three glossary entries. `_seed_terms` still writes a placeholder `VERDICTS[i % 3]` rotation for `difficulty`/`pairAccuracy` regardless of seed content — real term verdicts (204 terms, 🟢62/🟡31/🔴111) only reach the `term` table via the separate `scripts/load_terms.py` step run after seeding (see [e2e-data.md](../testing/e2e-data.md) and [terminology stage doc](../stages/terminology.md)). |
| [`precompute.py`](../../src/palimpsest/webapp/precompute.py) | Background first-pass scoring for uploaded documents (spec §5.6). Sequential, budget-guarded judge pass over the first 12 paragraphs; writes `kind='seed'`+`kind='cache'` atomically per paragraph. |
| [`translate.py`](../../src/palimpsest/webapp/translate.py) | Background first-pass AI translation for a source-only uploaded document (2026-07-05-translator). Mirrors `precompute.py`'s status-registry/cancellation pattern; writes `paragraph.target`/`seed_target` + an `origin='translate'` revision per paragraph, rolling 2-paragraph context, budget-guarded, one retry on a transient error. See "Translate" below. |
| [`migrate.py`](../../src/palimpsest/webapp/migrate.py) | Additive, idempotent schema migration for an existing (already-populated) prod DB — `CREATE TABLE IF NOT EXISTS`/guarded `ALTER TABLE`/backfill, one step per table/column: `target_revision`, `translator_config`, `grounding_config`, `glossary`, `term.trace_json`, `score.revision_id`. Runs on every app startup (FastAPI lifespan) and via `python -m palimpsest.webapp.migrate`. `db.py::SCHEMA` is still the source of truth for fresh DBs; this module exists because there is no other migration framework in the project — **every table/column added to `SCHEMA` needs a matching step here, or an already-populated prod DB never gets it** (2026-07-06: `grounding_config` shipped in `SCHEMA` without one, causing a prod 500 on `GET /api/grounding-config` — see [known_issues.md](../known_issues.md)). |
| [`export.py`](../../src/palimpsest/webapp/export.py) | Renders a document as a parallel-text file — `.xlsx` (openpyxl, paragraph-aligned, score-colored) or `.md` (a table). No DB writes. See "Export" below. |
| [`model_matrix.py`](../../src/palimpsest/webapp/model_matrix.py) | Single source of truth for the 8 demo models' capabilities and seed default params (`MATRIX`). Pricing is never hardcoded — fetched live from OpenRouter at runtime by `budget.py`. |
| [`model_params.py`](../../src/palimpsest/webapp/model_params.py) | Parses a model's `params_json` and keeps only the keys that model actually supports, per `model_matrix.MATRIX`; unknown keys are silently dropped (`ConfigDict(extra="ignore")`) — this is the CAPABILITY filter (`effectiveParams` in the wire DTO), separate from the WRITE-time key whitelist in `app._validate_params_whitelist` (§ Params whitelist below). |
| [`budget.py`](../../src/palimpsest/webapp/budget.py) | In-process spend/call guard for real OpenRouter calls (hard $2 cap, 200-call cap). `reserve()` atomically checks-and-increments under an `asyncio.Lock` before the network call; `settle()` corrects the reservation to the actual reported cost (generation-stamped, so a budget reset no-ops stale in-flight settles). |
| [`secrets_guard.py`](../../src/palimpsest/webapp/secrets_guard.py) | Boundary-aware detector for secret-like param keys (`api_key`/`token`/`secret`/…). Used both to reject secret keys written into a criterion/model's `params` bag (`_guard_params` in `app.py`) and to strip secrets out of the budget cost log (`budget.log_call`). Also holds `redact_error()`, which masks token-like substrings and caps length in free-text exception messages before they reach `budget_calls.jsonl` (`_judge_live`'s retry/terminal error logs). |
| [`llm/client.py`](../../src/palimpsest/llm/client.py) | Thin stateless wrapper over the OpenAI-compatible chat completions API. Single source of truth for all LLM access — no other module may import `openai` directly. Also exports `is_transient_error(exc)`, the retry-worthiness classifier (timeout/connection/429/5xx → retry; 4xx/parse errors/`CancelledError` → not), so callers like `webapp/app.py` don't need their own `openai` import just to classify an error. |

Database tables: `document`, `paragraph`, `criterion`, `model`, `score`, `issue`, `term`, `glossary`,
`grounding_config`, `translator_config`, `target_revision`.
Full DDL is in the contracts spec linked above (§4 for rev-4, §7.1 for the rev-5 delta). `document.origin` (`'seed'|'upload'`) distinguishes the
seeded demo document from user uploads; `paragraph.document_id` and `score`/`issue`/`term`'s `paragraph_id`
FKs carry `ON DELETE CASCADE`, so deleting a `document` row cascades to all its children in one statement
(required for `DELETE /api/documents/{doc_id}` — `PRAGMA foreign_keys=ON` is set, so this is not optional).
`document.id` and `paragraph.id` are `INTEGER PRIMARY KEY AUTOINCREMENT` — plain `INTEGER PRIMARY KEY`
lets SQLite reuse a deleted row's rowid for the next insert, which would let an orphaned background task
(see Precompute below) write scores against a recycled id belonging to an unrelated new document.
`score.revision_id` (rev-5, nullable) points at the `target_revision` row current when that score was
written; historical pre-rev-5 rows stay `NULL` (never backfilled — honest, not guessed).

## Add Evaluator / Add Model modals

"+ Add evaluator" opens `AddEvaluatorModal` (`data-testid="add-evaluator-modal"`, error `add-evaluator-error`) — Name, Model (select from registry), Weight (0–1, inline `Weight must be between 0 and 1` on out-of-range with Save blocked, no silent clamp), Color (auto via `unusedColor`, editable), Prompt (set once at creation; existing criteria's prompt stays a read-only preview). Saves via `onAddCriterion` with `enabled: false`. This replaces the old `handleAddEvaluator` phantom-row-then-edit flow entirely.

"+ Add model" opens `AddModelModal` (`add-model-modal`, `add-model-error`) — Name, Base URL (default `https://openrouter.ai/api/v1`), API key (password, optional), Params (JSON textarea, placeholder `{"max_tokens": 1536}`, inline error on invalid JSON). Replaces the old `window.prompt()` call.

Both modals surface server errors inline in the modal body rather than failing silently. Both render as a centered overlay via the same `.va-popover-backdrop.va-modal-backdrop` flex-centering mechanism as `UploadModal` (the `.va-popover` box nests inside the backdrop, which resets its `position: fixed` to `static` so it doesn't strand outside the viewport).

**Params badge:** the Model Registry's Params column renders a `N params` badge (`params-badge-{modelName}`) that toggles an expanded key/value view (`params-expanded-{modelName}`) on click; each badge toggles independently, and expansion state resets on refetch (local component state keyed by model name).

## Seed demo flag

`seed()` (`seed.py`) reads `PALIMPSEST_SEED_DEMO` from the environment: when truthy, only the 5 OpenRouter rows from `MATRIX` are inserted into `model` (the 3 dead `localhost:8001` vLLM rows are skipped); the default (`0`/unset) behavior — all 8 matrix rows — is unchanged, so existing local tests/e2e docs asserting `count(*)=8` keep working. All seed criteria point at `openai/gpt-5.4-mini`, which is OpenRouter, so the criterion→model FK resolves under both branches.

## Production rollout

Rolling the settings-rework branch onto the live server **never reseeds the DB** — `seed()` drops the whole SQLite file, destroying uploads, history, and any keys stored in model rows. The registry is cleaned with a targeted DELETE instead. Full procedure and rationale: [settings-rework spec §6](../superpowers/specs/2026-07-02-settings-rework.md).

**Current update procedure (rev-5, wave-5):** [deploy/update-server.sh](../../deploy/update-server.sh) automates a `dev-demo` rollout onto the owner's server (`72.56.109.228`) — git pull, frontend build, `demo.db` backup, image rebuild + restart of ONLY the `gse-demo` container, running `python -m palimpsest.webapp.migrate` against the live DB before it starts serving, disabling the retired `cultural` criterion (`UPDATE`, never `DELETE`), and forcing `temperature: 0` on the demo model rows via the live API. See [deploy/README.md](../../deploy/README.md) for the full step list and env vars.

1. **Backup first** (cheap, one file): `cp /opt/gse-demo/data/demo.db /opt/gse-demo/data/demo.db.bak`.
2. **FK pre-check — must return 0, otherwise stop:**
   ```sql
   SELECT COUNT(*) FROM criterion
   WHERE model_name IN (SELECT name FROM model WHERE base_url LIKE 'http://localhost%');
   ```
   (Seed criteria reference only `openai/gpt-5.4-mini`, so 0 is the expected answer; a non-zero count means a criterion points at a row about to be deleted.)
3. **Targeted cleanup** (the 3 dead vLLM rows): `DELETE FROM model WHERE base_url LIKE 'http://localhost%';` — executed via `docker exec … python`/`sqlite3` against the `/data` volume.
4. **Rollback** (one line): restore the backup — `cp /opt/gse-demo/data/demo.db.bak /opt/gse-demo/data/demo.db` — or re-INSERT the deleted rows from `model_matrix.MATRIX`.

## Improvement-loop semantics

The core loop is: **evaluate → inspect issues → apply-edit → re-evaluate**.

**Explicit re-evaluation / stale scores (2026-07-02).** `/evaluate` is a paid LLM call and is never triggered implicitly. Accept, Accept-all and manual paragraph edits (`saveParagraphTarget`) only apply the text change and set `paraEvalState[idx].stale = true` in the store — they never call `evaluateParagraph`. A re-judge happens only when the user presses the "Evaluate ↻" button. `ScoreChip` renders a `va-stale-badge` next to the cached badge, and `InspectorPanel` shows a hint ("Scores are for a previous version — press Evaluate ↻") whenever `evalState.stale` is true, so a paragraph with edited text but unrefreshed scores is always visibly marked. `evaluateParagraph` clears `stale` back to `false` on both the loading transition and the success write (a failed call leaves the prior `stale` value untouched via the existing state spread).

**Manual re-evaluate affordance (dead-paragraph revival).** `InspectorPanel`'s header has an always-visible "Evaluate ↻" button (`data-testid="evaluate-para"`, disabled while `evalState.loading` or when no paragraph is selected) that calls the store's `evaluateParagraph(paragraph.id, selectedParaIdx)` directly, independent of issue state. This is now the **only** path to a live re-judge — it revives paragraphs whose precompute was skipped or whose judges all failed, and it is also how a user clears a `stale` badge after accepting suggestions or editing text.

**Retry only what failed.** When a live pass returns a non-empty `failedCriterionIds`, the inspector's warning banner ("Failed: style, cultural") carries a "Retry failed ↻" button (`data-testid="retry-failed"`) that calls `evaluateParagraph(pid, idx, failedCriterionIds)`. The store threads an optional `criterionIds` list into `POST /evaluate` (`{criterionIds}`), so the retry re-runs **only** the failed criteria — the already-scored ones are neither re-judged nor re-billed. The endpoint returns the full latest score set regardless (`_para_score_views`), so `applyEvalToParag` merges the fresh scores over the surviving ones and the banner clears when the retry succeeds.

Score kinds are set once at write time and never changed, with one exception: `reset_document` flips `live` → `archived` (see Reset below) — this is the only mutation, and it never deletes.

- `seed` — written by `seed.py` at DB init for the seeded document; represents the baseline translation quality. For `origin='upload'` documents, the equivalent baseline is written by `precompute.py` (see below) instead.
- `live` — written by `/evaluate` on a successful LLM call; represents the latest human-edited state.
- `cache` — written by `seed.py` as pre-computed uplift (+1.5, capped at 10) for the seeded document; used as fallback when all LLM judges fail in `/evaluate`. `precompute.py` writes `kind='cache'` rows too, but as honest passthrough copies of its own `seed` values — no artificial uplift for uploads.
- `archived` — a former `live` row after `POST /api/documents/{doc_id}/reset`; preserved for the prediction-preservation invariant (see [known_issues.md](../known_issues.md)) but excluded from every active view (`_para_score_views` reads `kind IN ('seed','live')` only).

The latest score shown to the user is determined from `kind IN ('seed', 'live')` ordered by `created_at DESC`. The `kind='cache'` rows are never mixed into this history view; they are only returned by `/evaluate` when the live call fails, tagged with `cached=true` and `cachedAt` in the response.

**`aggregatePrev` (old→new delta).** `POST /api/paragraphs/{pid}/evaluate` and its cache-fallback response both include `aggregatePrev: number | null` — the paragraph's aggregate from `kind IN ('seed','live')` immediately before this evaluate call's own rows are written; `null` means this is the paragraph's first-ever score. The frontend uses it (in preference to the static `aggregateBaseline`) to show a delta badge only between an old and a new score, never from a stray zero — see [contracts spec §5.1/§5.5](../superpowers/specs/2026-07-02-custom-pair-upload-design.md).

**Transient-error retry (per criterion).** Before a criterion is counted as failed, `_judge_live` retries transient provider errors — `TimeoutError`/`asyncio.TimeoutError` (the `EVAL_TIMEOUT` wait_for firing), `openai.APITimeoutError`/`APIConnectionError`/`RateLimitError` (429), and 5xx (`InternalServerError` or an `APIStatusError` with `status_code >= 500`). Classification lives in `palimpsest.llm.client.is_transient_error` (`app.py` imports it instead of `openai` directly; `webapp/` has no direct `openai` import, enforced by `tests/test_llm_transient.py::test_webapp_has_no_direct_openai_import`). It retries `EVAL_RETRIES` times (default 2, env `PALIMPSEST_EVAL_RETRIES`) with exponential backoff (`EVAL_BACKOFF * 2**attempt`, base 0.5 s, env `PALIMPSEST_EVAL_BACKOFF`). Deterministic errors — a bad request, auth failure, or unparseable JSON (`JSONDecodeError`) — are **not** retried, since a retry would burn another paid call and fail identically. The single budget reservation made before the loop covers every retry (a retry only fires after the prior attempt was billed $0), and the terminal outcome settles once — to the real cost on success, to `0.0` on final failure. Each retry and the terminal error are logged to the budget JSONL with the error type/message (`status: "retry"|"error"`, `error: "<Type>: <msg>"`) so failures are diagnosable. This makes a plain re-evaluate resilient to the latency-tail / rate-limit blips that otherwise surfaced as a dead-end "Failed: style, cultural" banner — see [known_issues.md](../known_issues.md). Both sites also emit `logger.warning` (module logger `palimpsest.webapp.app`, stdlib `logging.getLogger(__name__)`) with the criterion id, model name, attempt count, and the same redacted error string — the budget JSONL is not tailed live, so an operator watching plain `uvicorn` output would otherwise see nothing when judges fail.

**Error redaction.** The `error` field logged at both `_judge_live` sites is passed through `secrets_guard.redact_error()` before it reaches `budget_calls.jsonl` — `openai.AuthenticationError`'s message echoes a bad API key back verbatim ("Incorrect API key provided: sk-..."), so the raw exception text is not safe to log as-is. `redact_error` masks `sk-`/`sess-`/`pk-`-style keys and other long opaque token-like runs, and caps the message to 300 chars. See [known_issues.md](../known_issues.md) "RESOLVED 2026-07-02: API key leaked verbatim".

**Cache fallback protocol:** if every LLM judge in `/evaluate` raises an exception (after its retries are exhausted), the endpoint reads `kind='cache'` rows and returns them tagged `cached=true`. The cached response reports `failedCriterionIds: []` — every criterion received a cached value, so nothing failed from the client's view (the live judges that raised are an internal detail). If no cache rows exist either, the endpoint falls through to the normal response and returns the paragraph's existing `kind IN ('seed','live')` scores unchanged, with `cached=false` (not an empty result). This means the app remains usable without a live API key.

**Dismissed/accepted issues are not resurrected on re-judge.** Before inserting a fresh `kind='live'`, `status='open'` issue row, `/evaluate` checks whether a `dismissed` or `accepted` issue (`status IN ('accepted','dismissed')`) already exists for the same `paragraph_id` + `criterion_id` + `target_fragment`; if so, the insert is skipped. This prevents a re-judge from re-surfacing a fragment the reviewer already dismissed or accepted as a brand-new open duplicate sitting next to the closed one. A genuinely different fragment on the same criterion/paragraph still inserts normally. The guard is deliberately narrow: `superseded`/`archived`/`outdated` rows are NOT user decisions, so they must not block re-detection — see the prediction-preservation invariant below.

**Prior open live issues are superseded, not deleted, on re-judge.** Before inserting fresh issues for a criterion, `/evaluate` flips any existing `paragraph_id`+`criterion_id` row with `kind='live', status='open'` to `status='superseded'` (`UPDATE`, not `DELETE`) — the prior judge run stays in the DB as history but drops out of `_para_issues`' output (see below). This is the prediction-preservation invariant (owner hard invariant, wave-4): no user path may destroy an LLM prediction.

**Reset:** `POST /api/documents/{doc_id}/reset` restores `paragraph.target` from `paragraph.seed_target`, archives `kind='live'` scores and issues (never deletes — see prediction-preservation invariant below), reopens seed issues, and bumps `document.version`. Seed **and** cache rows are untouched, so the canned post-fix uplift survives repeated resets. Both operations ignore prior `status`: **all** `kind='live'` scores flip to `kind='archived'` and **all** `kind='live'` issues flip to `status='archived'` regardless of whether they were `open`/`accepted`/`dismissed`/`outdated`/`superseded`, and **all** `kind='seed'` issues are forced back to `open` regardless of prior status — a previously-dismissed seed issue reopens too. Returns 409 if an `/evaluate` call is in flight — the in-flight check reads `_evaluating` outside the write lock (a benign TOCTOU window, acceptable for the single-user demo).

**Prediction-preservation invariant (owner hard invariant, wave-4).** No user path (`/evaluate`, `/reset`) may `DELETE` a `score` or `issue` row — LLM predictions are irreproducible and needed for future metrics. The only user-path mutations are status/kind flips: `/evaluate` sets a superseded prior live issue to `status='superseded'`; `/reset` sets prior live scores to `kind='archived'` and prior live issues to `status='archived'`. `_para_issues` (the read path feeding every `issues` field in the API) explicitly drops `superseded` and `archived` rows — and drops a `seed`+`open` row too once its criterion has a `live` score, since that seed row is implicitly superseded by the live re-evaluation. `_para_score_views` drops `archived` scores the same way, via `kind IN ('seed','live')`. The only remaining `DELETE` on these tables is the FK `ON DELETE CASCADE` triggered by deleting a whole document (`DELETE /api/documents/{id}`) — out of scope for this invariant (a one-shot upload cleanup, not a prediction-destroying edit). `seed()` refuses to reseed (`db.init_db(reset=True)`, which unlinks the DB file) a non-empty DB unless `PALIMPSEST_SEED_FORCE=1` is set — a code-level guard against an operator accidentally wiping live predictions via a re-seed.

Dismiss персистится этим PATCH; reset реоткрывает seed-issues (kind='live' dismissed переводятся в status='archived' вместе с остальными live-строками — не удаляются, см. prediction-preservation invariant выше).

Одиночный Accept = apply-edit, БЕЗ re-judge (только `markStale(paraIdx)`); Accept all = все apply-edit параграфа, тоже без re-judge — один `markStale` в конце. `applyIssueEdit` возвращает `'applied' | 'outdated' | 'failed'`: сервер отвечает 422 `fragment_not_found`, только если фрагмент реально перекрыт предыдущей правкой (whitespace-расхождения матчинг переживает — см. "Fragment matching" ниже); в этом случае issue получает статус `outdated` (оптимистично + PATCH на сервер), а не откатывается в `open`. Сервер также отвечает 422 `not_open`, если issue уже не `open` (принят/отклонён/устарел до этого запроса, например при гонке двух вкладок) — в этом случае фронт откатывает оптимистичный флип обратно к статусу ДО попытки (не `outdated`, чтобы не приписать неверную причину), target не трогается. `acceptAllIssues` возвращает `{applied, outdated}` вместо старого `window.alert`; инспектор показывает тусклую строку "Applied N · M outdated (overlapped by earlier edits)" рядом с кнопкой Evaluate. Server-side инвалидация при apply: успешный `apply-edit` проходит по остальным `open`-issues абзаца тем же whitespace-толерантным матчером; недостижимый фрагмент → `outdated`, обновлённые issues возвращаются в `siblingIssues` и вливаются фронтом — но фронт применяет статус соседа из `siblingIssues` только если локальная копия всё ещё `open` (защита от гонки: если пользователь параллельно сам dismiss'нул соседа, серверный `outdated` не должен его перезаписать). **И попап, и инспектор показывают ТОЛЬКО `open`-issues (wave-4, Б2)** — двухчастная видимость в обоих: `open` — активна, всё остальное (`accepted`/`dismissed`/`outdated`/`superseded`/`archived`) скрыто из UI сразу по факту решения пользователя (resolved-issue исчезает из панели, а не рисуется зачёркнутым «как история»); в БД строка остаётся нетронутой — см. prediction-preservation invariant выше, UI-скрытие не имеет отношения к сохранности данных. Issue без конкретной правки (`suggestion` пуст — совет, не drop-in замена) рендерится как пассивная read-only заметка (бейдж критерия + explanation, БЕЗ кнопок Accept/Dismiss) вместо dismiss-only карточки, и в попапе, и в инспекторе. Попап автозакрывается, как только его производный список карточек опустошается (все issues абзаца приняты/отклонены/отфильтрованы) — `useEffect` на `popoverIssues.length === 0`. Перекрытые соседи умирают в момент ПЕРВОГО принятия, а не при собственной попытке apply. Re-judge запускается только явным нажатием "Evaluate ↻" — он же перегенерирует список issues под новый текст.

Попап (`IssuePopover`) закрывается не блокирующим fullscreen-backdrop'ом, а `document`-level `mousedown`-листенером (capture phase) плюс Escape: клик вне попапа закрывает его И продолжает всплытие к своей цели — один клик по другой строке одновременно закрывает старый попап и выбирает/открывает новую строку/подчёркивание, вместо того чтобы первый клик "тратился" на закрытие backdrop'а.

**Issue lifecycle (user-initiated, PATCH-reachable):** `open → accepted` (только через apply-edit — он же переписывает target, ТОЛЬКО если issue уже `open`; иначе 422 `not_open`), `open ↔ dismissed` (PATCH, обратимо), `open → outdated` (PATCH при собственном 422 batch-accept; либо как побочный эффект apply-edit соседа — сервер инвалидирует перекрытых `open`-соседей того же абзаца в момент ПЕРВОГО принятия, см. таблицу роутов выше). `PATCH /api/issues/{iid}` принимает `open | dismissed | outdated`; `accepted` через PATCH — 422 `invalid_status`; PATCH по уже-`accepted` issue — 409. Два дополнительных статуса недостижимы через PATCH, только через сервер: `open → superseded` (`/evaluate`, см. prediction-preservation invariant выше) и `open → archived` (`/reset`).

Dismiss failure (PATCH не подтвердился) откатывает статус на `open` И проставляет `paraEvalState[idx].error`, используя тот же баннер `va-inspector-warning`, что и ошибки evaluate.

## Precompute

`POST /api/documents` sets the in-memory precompute status via `precompute.mark_skipped(doc_id)` or `precompute.mark_started(doc_id, n_paragraphs)` (the latter sets `{status: 'running', done: 0, planned: min(N, 12), succeeded: 0}`) **before** building the response dict, so the 201 body's `document.precompute` field always reflects the real status immediately — never `null`. The background task itself is started via `precompute.launch(doc_id, _judge_live)` (`precompute=true` only), which wraps `asyncio.create_task(run(doc_id, judge_live))` and keeps a strong reference in `precompute._tasks[doc_id]` (an `asyncio.Task` is otherwise only weakly held and can be garbage-collected mid-run); `launch` is called after the response dict is built. `create_document` never touches `precompute._status`/`precompute._tasks` directly — `mark_started`/`launch` are the only entry points. It scores the first 12 paragraphs sequentially (not `gather`), writing `kind='seed'` (baseline scores + open issues) and `kind='cache'` (fallback copies) atomically per paragraph. Every call goes through `budget.reserve()`/`settle()` plus a global sub-cap (`PALIMPSEST_PRECOMPUTE_CALLS`, default 80) checked-and-incremented under `budget._lock` before each call — no second locking scheme. Before each paragraph write, the loop re-checks **inside** `db._lock` that (a) the document still exists and (b) no score rows exist yet for that paragraph (TOCTOU guard): if the document was deleted, or a live `/evaluate` raced ahead, during the LLM calls, the precompute results for that paragraph are discarded, never written. In-memory status (`{status, done, planned, succeeded}`, `status` one of `running|done|stopped|skipped`) is exposed via `document.precompute` in the DTO for `origin='upload'` docs and lost on process restart. `succeeded` counts paragraphs whose scores were actually written (or already present); a run that was requested but ends with `succeeded == 0` (e.g. every judge call failed for want of an API key) is surfaced in the document view as a dim inline notice pointing the user at the per-paragraph "Evaluate ↻" affordance — without it the failure was silent: unexplained "—" score chips.

**`errorReason` (rev-5).** When a precompute run ends `done` with `succeeded==0` (planned>0), `_status[doc_id]` gains `error_reason` — `no_api_key`, `budget_exhausted`, or `all_failed` — classified from the exception the first failing paragraph raised (`precompute._classify_failure`; `translate._classify_failure` mirrors it for the translate status block). The wire DTO camelCases it to `errorReason`. This turns the previously-unexplained "ran and wrote nothing" banner into "Precompute skipped: no API key configured" / "…: budget cap reached" in the UI, instead of a bare dash with no hint.

**Delete cancels in-flight precompute.** `DELETE /api/documents/{doc_id}` calls `precompute.cancel(doc_id)` after the DB delete commits: it cancels the task in `_tasks` (if still running) and pops the `_status` entry. This stops further paid judge calls immediately and, combined with the AUTOINCREMENT ids above, closes both halves of the "spend after delete" / "id-recycling corruption" risk — any task that is already past its last cancellation checkpoint still hits the `_document_exists` re-check in `_write_paragraph` before writing.

See [contracts spec §5.6](../superpowers/specs/2026-07-02-custom-pair-upload-design.md#56-прогрев-кеша-precompute) for the full design.

## Translate

`POST /api/documents {translate: true}` lets a user upload SOURCE ONLY and have it translated by the configured translator model+prompt (`translator_config`, a singleton mirroring `grounding_config`) instead of pasting a translation. Every `paragraphs[].target` in the body must be empty — a mix is `422 mixed_targets` — and the server **forces `precompute:false`** regardless of the body's flag: precompute would otherwise run a paid judge pass over 12 empty targets and permanently record a garbage `kind='seed'` baseline (`_already_scored` then skips those paragraphs forever). Paragraphs are created with `target=seed_target=''` and no `target_revision` yet — `translate.py` writes the first one (`origin='translate'`) once each paragraph actually gets translated.

`translate.run_translation(doc_id, client_for)` (module `translate.py`) walks paragraphs in order, skipping any that already have a `target` (idempotent resume — a repeat `POST .../translate` only fills in what's still empty). Context is a rolling window of the last 2 translated paragraphs (trimmed to 2000 chars), fed into the user prompt as "Context — previous translation". Each call goes through `budget.reserve()`/`settle()` like `_judge_live`, retries once on a transient error (`is_transient_error`), and a hard `BudgetExceeded` mid-run stops the loop immediately (`status='failed', errorReason='budget_exhausted'`) rather than marking the untried remainder "done". `POST /api/documents/{doc_id}/translate` does a rough pre-check (`budget.estimate` against the configured model+params) before even launching the background task, so an already-exhausted budget never starts one; the per-call `reserve()` remains the hard guarantee regardless.

Concurrency: `translate._translating: set[int]` mirrors `app._evaluating` — while a doc_id is in it, `POST /api/paragraphs/{pid}/evaluate` and `POST /api/documents/{doc_id}/reset` both 409 `translation_in_progress`, and `DELETE /api/documents/{doc_id}` calls `translate.cancel(doc_id)` (same pattern as `precompute.cancel`) to stop the background task and discard it from the set.

`app._client_for(conn, model_name, params_override=None)` grew a third parameter for this: `translate.py` and `_grounding_judge_live` pass their own config's `params_json` as `params_override`, which REPLACES the model registry row's own params entirely (the registry-row params are still what `_judge_live`/the Test probe use — no override there). Before this, `_grounding_judge_live` computed its budget estimate from `grounding_config.params_json` but built the actual client from the model row's own params — a no-op-params bug now fixed by the same mechanism (see [known_issues.md](../known_issues.md)).

## Revision history & best

Every write to `paragraph.target` — upload, a manual PATCH (only if the text actually changed), apply-edit, translate, reset, and restore — also inserts a `target_revision` row (`{paragraph_id, text, origin, created_at}`; `origin` one of `seed|upload|edit|apply_edit|translate|restore`). `seed.py` writes one at seed time too, so a freshly-seeded DB and a migrated prod DB have the same shape of history. `score.revision_id` is stamped at all three score-INSERT sites (`/evaluate`, `precompute._write_paragraph`, `seed.py`) via `db.latest_revision_id(conn, pid)`.

**Best revision:** `_best_revision(conn, pid)` (`app.py`) picks `argmax(aggregate)` over `kind IN ('seed','live')` scores with a non-null `revision_id` — `kind='cache'` is excluded, it's a synthetic seed-uplift preview, never a real judged revision. Exposed as `paragraph.best: {aggregate, revisionId, createdAt, isCurrent} | null` in the document DTO; `null` means the paragraph has no scored revision yet (e.g. a legacy pre-rev-5 row, or freshly translated text nobody has evaluated). This directly answers the owner's "re-evaluation can regress — never lose the best version" concern: nothing is auto-restored, but the best score+its text are always one `GET /api/paragraphs/{pid}/revisions` + `POST .../restore` away.

`GET /api/paragraphs/{pid}/revisions` lists every revision (newest first) with `aggregate` = the best score attached to that specific revision (`null` if never evaluated), plus `isBest`/`isCurrent` flags. `POST /api/paragraphs/{pid}/restore {revisionId}` sets `target` to that revision's text and writes a NEW `origin='restore'` revision (restoring is itself a tracked event, not a rewind) — it does **not** copy scores; the paragraph's chip goes back to "not scored" honestly until the next explicit `/evaluate`. 404 for an unknown revision id, 409 if the revision belongs to a different paragraph.

## Export

`GET /api/documents/{doc_id}/export?format=xlsx|md` (module `export.py`) streams a parallel-text file — no DB writes, no persisted state. `.xlsx` (openpyxl): one row per paragraph (`¶`, `Source · <lang>`, `Translation · <lang>`, `Score`), header row styled dark (`#1F2035`/`#C0CAF5`, frozen), a grey meta row underneath (title/langs/export date, merged A:D), and the Score cell colored by the same thresholds as the UI's score chip (≥8 green, 6–8 yellow, <6 red). `.md` emits a GFM table with `|`/newline escaping. Both read the SAME `_rows()` helper (latest `kind IN ('seed','live')` aggregate per paragraph) — no format-specific data path to drift. 404 for an unknown document, 422 for an unrecognized `format`. Filename is `{slugify(title)}-{doc_id}.{ext}` (`slugify` falls back to `document` if the title has no ASCII-alnum characters, e.g. a fully-Cyrillic title).

## Params whitelist (rev-5)

`POST/PUT /api/models`, `PUT /api/grounding-config`, and `PUT /api/translator-config` all run `app._validate_params_whitelist(params)` — a fixed set of accepted keys with type/range checks (`max_tokens` 1..32768, `temperature` 0..2, `top_p` 0..1, `top_k`/`seed` int, `min_p` number, `enable_thinking` bool, `reasoning: {effort: low|medium|high, max_tokens: int>=0}`) — before the write lands. An unrecognized key is `422 {"detail": "unknown param: <key>"}`; before this it was silently saved then silently dropped by `ModelParams`'s capability filter (`extra="ignore"`), so a mistyped param looked accepted but did nothing. The pre-existing secret-key guard (`_guard_params`, HTTP 400) still runs FIRST — a key can be both secret-like and off-whitelist (e.g. `api_key`), and the security rejection takes precedence over the "unknown param" one.

The DB and budget JSONL live on the `/data` volume (`PALIMPSEST_DB`, `PALIMPSEST_BUDGET_LOG`); seed the volume once with a locally-seeded `demo.db` or run `python -m palimpsest.webapp.seed` inside the container. Deployed instance: `gse-translation.ru` (container `gse-demo` on the `grader-net` docker network behind Caddy; the legacy viewer container `gse-viewer` stays up, reachable at `viewer.gse-translation.ru` once its DNS record exists).

## Subtleties

- **Accept with empty suggestion is rejected (not destructive).** `POST /api/paragraphs/{pid}/apply-edit` replaces `target_fragment` with `suggestion`. When `suggestion` is empty or whitespace the endpoint returns **422 `no_suggestion`** and the translation is left untouched — the flagged fragment is never silently deleted. Of the 75 seed issues (post [seed-refresh](../superpowers/plans/2026-07-02-seed-refresh.md), one baseline pass per criterion × 15 paragraphs), 29 have `suggestion = ""` (the judge flagged a problem but proposed no rewrite); the frontend renders these as passive read-only notes (criterion badge + explanation, no Accept/Dismiss buttons at all — wave-4 Б2, was a dismiss-only card before), and Accept-all skips them.
- **Accept on a non-open issue is rejected, not a silent re-apply.** The endpoint loads the issue and checks `status=='open'` before touching anything; a second accept on an already-`accepted` issue, or an accept on a `dismissed`/`outdated` one, returns **422 `not_open`** with the target and issue status byte-identical to before the call. Without this guard the fragment match would run against the CURRENT (already-edited) target and could splice text a second time or hit an unrelated look-alike span.

- **Advice-text guard (2026-07-02).** A judge sometimes puts *advice* in `suggestion` ("Consider 'temple centers' with a brief gloss if needed", "Use 'debt bondage', which is the standard...") instead of a drop-in replacement — accepting it splices the advice into the translation. Three defenses: (1) `scoring_system_prompt()` preamble states the **suggestion contract** — `suggestion` is a verbatim, target-language replacement for `problematic_fragment`; advice goes in `explanation`; no concrete replacement -> empty string. (2) A pure `looks_like_advice()` heuristic (English advisory lexicon for ru->en completeness + a language-agnostic quoted-alternative structural signal) drives `sanitize_issue()`, which is called on **all three ingest paths** — `_issue_from()` (live `/evaluate` + precompute) and the seed INSERT loop in `seed.py`. A flagged suggestion is moved to the end of `explanation` as `Advice: ...` and the field is emptied, so `apply-edit` returns 422 `no_suggestion` and the resulting empty-`suggestion` issue falls into the passive-note render path in `InspectorPanel`/`IssuePopover` (no Accept, no Dismiss — see "Prediction-preservation" section above) — no frontend change needed for this guard specifically. `sanitize_issue()` is idempotent (a second pass is a no-op; `Advice:` is not duplicated) and coerces a non-`str` `suggestion` (e.g. `None`, or a stray JSON number from a malformed provider payload) to `""`/`str(value)` before the heuristic runs, so a malformed row can't crash `seed()`. (3) **`apply-edit` itself re-runs `looks_like_advice()` on the stored `suggestion`** before splicing, independent of `sanitize_issue` — this is the second line of defense for a **legacy row that predates the guard** (a pre-guard prod row can carry a non-empty advice suggestion that no ingest path ever sanitized): such a row now 422s `advice_suggestion` instead of being spliced in, the target is left untouched, and the issue status is unchanged. `POST reset` reopens seed issues and reinstates `seed_target`, but never rewrites `suggestion`/`explanation` — a reopened legacy advice row is still caught by defense (3) at apply time, so the "reset reopens un-acceptable advice" property holds even for rows the seed-time guard never touched. Full data repair is the `feat/seed-refresh` re-seed (guard merges first). The frontend treats `advice_suggestion` exactly like the existing `fragment_not_found`/`no_suggestion` 422s — generic 422 handling in `applyIssueEdit` (`store.ts`) marks the issue `outdated` and Accept-all's summary counts it as skipped, no alert.

- **Fragment matching is whitespace-tolerant.** `_splice_suggestion` tries an exact substring first; on a miss it re-searches the fragment's tokens joined by `\s+` (`re.escape`-d), so spacing reflow from an earlier accepted edit in the same batch no longer fails the apply. Only when the tokens are genuinely gone (the fragment was overlapped/rewritten by a prior edit) does the endpoint return **422 `fragment_not_found`** — the frontend then marks the issue `outdated` (see "Improvement-loop semantics"). The same matcher is used for sibling invalidation on a successful apply: a probe splice (`_splice_suggestion(new_target, frag, frag)`) returning `None` means the sibling's fragment is overlapped.

- **Boundary-word de-duplication on apply.** A judge suggestion sometimes repeats the word immediately before or after the target fragment (fragment `drawn into buying and selling`, suggestion `partly incorporated into the land market`, with an existing `partly` just before). `apply-edit` (`_splice_suggestion`) drops that duplicated boundary word so the result reads `…were partly incorporated…`, never `…partly partly…`. A non-numeric `issueId` returns 404 (it can match no row), not 500.

- **Single-writer concurrency.** All DB writes are serialized by a single `threading.Lock`. The app is designed to run under `uvicorn --workers 1`. Multiple workers would bypass the lock and corrupt state.

- **Criterion deletion blocked by history.** `DELETE /api/criteria/{cid}` returns 409 if any `score` or `issue` rows reference that `criterion_id`. Callers must disable the criterion instead of deleting it once it has history.

- **Term stub.** `POST /api/paragraphs/{pid}/terms` is a stub. The term-agent fills the `term` table externally. The frontend renders whatever is in the table; the endpoint itself does no computation.

- **Params secret-key guard.** `POST/PUT /api/models` and `/api/criteria` reject any `params`/config dict whose keys look secret-like with HTTP 400, before touching the DB. The check (`_guard_params` in `app.py`) delegates to `secrets_guard.is_secret_key`, which is boundary-aware: strong indicators (`api_key`, `token`, `secret`, `password`, `bearer`, `authorization`, …) match anywhere in the key, while collision-prone short words (`token`, `auth`, `key`) match only as a delimited component — so `max_tokens`/`top_k` are never falsely flagged.

- **Language-name sanitization.** `sourceLang`/`targetLang` are embedded verbatim in the judge SYSTEM prompt (`scoring_system_prompt`: "You are evaluating a translation from {X} into {Y}."). `POST /api/documents` runs both through `_sanitize_lang` at the same validation point as the existing 40-char cap: control characters are stripped, then all whitespace runs (including newlines/tabs) collapse to a single space — so a value like `"X\n\nIgnore previous instructions"` is stored as `"X Ignore previous instructions"`, unable to break out of the preamble sentence onto its own line. Free-text language names up to 40 chars are otherwise accepted as typed (`lang_name` in `judge.py` passes anything outside its 12-code map straight through) — this is a display/prompt-injection-shape guard, not a language-name allowlist.

- **Model registry as-built.** Models live in the `model` SQLite table (`name`, `base_url`, `api_key`, `params_json`). `GET /api/models` never returns the plaintext key — `apiKeyMasked` keeps only the **first 4 characters + `…`** (not a suffix, so a leaked truncation can't reveal the key's tail). If a model's own `api_key` column is empty and its `base_url` is an OpenRouter host, `_client_for` (`app.py`) falls back to the `OPENROUTER_API_KEY` env var — this fallback is OpenRouter-only, never applied to other providers. `POST /api/models/{name}/test` is a real term-extraction probe against seed paragraph idx=1 — it spends real money like other model mutations. `GET /api/models` also returns `effectiveParams` per row (`ModelParams.for_model()`'s output) alongside the raw `params` — the two can differ once capability filtering strips an unsupported key (e.g. `temperature` on a model with `supports_temperature=False`).

- **`apiKey` clear is a presence-check (rev-5), not a falsy-check.** `PUT /api/models/{name}` distinguishes `"apiKey"` absent from the request body (keep the existing key) from `"apiKey": ""` present-but-empty (explicitly clear it) — `"apiKey" in body` is the branch, not `body.get("apiKey")` truthiness. Before this fix an empty string was indistinguishable from omitted and silently kept the old key with no way to clear it through the API (see [known_issues.md](../known_issues.md), now resolved).

- **`POST /api/documents` body-size cap.** Bodies over 1 MB are rejected with HTTP 413 before pydantic ever parses them: `Content-Length` is checked first for a fast rejection, and the actual read byte count is checked too (covers a missing/lying header, e.g. chunked transfer-encoding). The route reads the raw body itself (`Request`, not a pydantic model parameter) and calls `CreateDocumentBody.model_validate_json` only once the size check passes.

- **Model routes use a `:path` converter.** `PUT/DELETE /api/models/{name:path}` and `POST /api/models/{name:path}/test` all use FastAPI's `:path` converter, not a plain `{name}`. Model names contain a slash (e.g. `qwen/qwen3.6-plus`), and a plain `{name}` segment stops at the first `/`, causing a 404.

- **Budget settle takes the same lock as reserve.** `settle()` corrects a reservation to the actual reported cost under the same `asyncio.Lock` as `reserve()`, so concurrent `/evaluate` coroutines never read a torn `spent` value. Spend is reset via `POST /api/budget/reset` — no process restart required.

- **Budget generation counter guards against a stale settle.** `reserve()` returns the current `_STATE["generation"]`; `settle(reserved, actual, generation)` requires that generation back and no-ops the spend-delta if it no longer matches — `reset()` (a `/api/budget/reset` call mid-run, or test isolation) increments the generation, so a call reserved *before* a reset can no longer perturb the freshly-reset spend when its `settle()` fires *after*. The `calls` counter is never rolled back by a stale settle either way — `settle()` never touches `calls`, only `spent`. A hard provider error in `_judge_live` (the live-judge path inside `/evaluate`) settles to `0.0` (not `None`) so a failed call releases its worst-case reservation instead of holding it for the rest of the process's life; `POST /api/models/{name}/test`'s error path keeps its existing `settle(est, None, gen)` semantics (worst-case reservation held) unchanged.

- **Term EN-highlight staleness after a live edit (accepted limitation).** A term's EN span anchors to `targetSurface` found inside the *current* translation text (`buildDecorations` in `review-extension.ts`, re-run on every doc change). If a live edit removes or rewrites that substring, the span for that term silently goes dark — no color, no dot — until the next full re-render restores a matching occurrence. This is the same accepted semantics as judge underlines that no longer match their `targetFragment` after an edit; it is not fixed here. Cross-hover and the RU-side `difficulty-*` badge (driven by `charStart`/`charEnd`, not text search) are unaffected.

- **Test probe is never a 5xx.** `POST /api/models/{name}/test` returns 404 only for an unknown `name`. Every other outcome — missing api key/env, timeout, API error, unparsable model output, or a budget block — is `200 {ok:false, message:<reason>}`, mirroring the `/evaluate` cache-fallback philosophy (a failed real call is a reported outcome, not a server error). The full `TestModelResult` shape is in the [contracts spec](../superpowers/specs/2026-06-30-demo-contracts.md#2-rest-api-frontend--backend).
