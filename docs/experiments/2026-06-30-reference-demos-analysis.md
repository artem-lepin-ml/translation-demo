# Анализ референсных demo-систем (для дизайна Palimpsest)

Up-link: [docs/pipeline.md](../pipeline.md) · родственный документ: [teardown-аудит](../reports/2026-06-emnlp-research-teardown-audit.html) · [terminology-glossary-research](2026-05-18-terminology-glossary-research.md)

## Зачем этот документ

Мы строим demo-track приложение Palimpsest: живой двуязычный (RU→EN) редактор оценки перевода на TipTap, несколько настраиваемых LLM-судей (каждый скорит абзац + выдаёт span-карточки Accept/Dismiss) и KG-слой терминологии (🟢🟡🔴 по Wikidata. Прежде чем фиксировать дизайн, я (Артём) хочу **вживую** посмотреть ближайшие чужие demo и решить, что из их UX заимствовать.

Этот файл — рабочая таблица для этого. **Заполняю я сам**, проходя по ссылкам; Claude держит ссылки актуальными и пишет совет в поле «💬 Совет» по каждой системе. Решения отсюда уходят в спеку нового бэкенда и в [teardown-аудит](../reports/2026-06-emnlp-research-teardown-audit.html).

Как пользоваться:
- **🔗 Ссылки** и **💬 Совет** — заполнено Claude (поддерживаю в актуальном виде).
- **👀 Что смотреть вживую** — конкретные экраны/взаимодействия, на которые стоит обратить внимание (Claude).
- **✅ Вердикт** и **🎯 Что берём** — пустые, заполняю я после просмотра.

Легенда статуса демо: **🟢 live** (есть рабочий хостинг, кликаешь и смотришь) · **🟡 local** (только репозиторий, надо поднять у себя) · **⚪ paper-only** (только статья, публичного UI нет).

## Карточки систем

### 1. Translation Canvas — ближайший прецедент карточек-правок

🔗 [paper (EMNLP 2024 demo)](https://aclanthology.org/2024.emnlp-demo.36/) · [`pip install translation-canvas`](https://pypi.org/project/translation-canvas/)
Статус: 🟡 local (ставится через pip, поднимается локально; публичного хостинга нет).

👀 **Что смотреть вживую:** как именно рендерится span-подсветка + карточка с NL-объяснением ошибки; цвета по категориям ошибок; side-by-side раскладка; переход «ошибка → фрагмент в тексте». Это самое близкое к нашим Accept/Dismiss-карточкам.

💬 **Совет:** это наш главный ориентир по карточкам, НО у них batch над одним хардкоженным InstructScore — нет живого цикла и нет мульти-судьи. Смотри на *форму* карточки (span + объяснение + категория), а наша новизна — что таких потоков несколько (по судье) и они живые. Обрати внимание, не перегружен ли их UI, когда ошибок много на абзац — у нас та же проблема будет.

### 2. Thresh — span-выбор по символьным офсетам

🔗 [thresh.tools (live)](https://thresh.tools) · [github davidheineman/thresh](https://github.com/davidheineman/thresh)
Статус: 🟢 live — можно открыть и потыкать прямо сейчас.

👀 **Что смотреть вживую:** механику выделения span (`getSelection → [start,end]`, хранение как символьные индексы); как YAML-конфиг типологии превращается в набор кнопок/категорий разметки; экспорт аннотаций.

💬 **Совет:** бери отсюда **инженерный приём span-выбора по char-offset** — это ровно то, что нам нужно для якорения карточек к тексту в TipTap (хранить правки как символьные индексы, а не как DOM-узлы). Идея «оценщик = декларативный объект, из которого выводится UI» — тоже отсюда (их YAML-типология). Это offline-аннотатор, не live-eval, так что весь их workflow нам не нужен — только два этих паттерна.

### 3. MATEO — вкладки-оценщики над общим списком сегментов

🔗 [lt3.ugent.be/mateo (live)](https://lt3.ugent.be/mateo/) · [github BramVanroy/mateo-demo](https://github.com/BramVanroy/mateo-demo)
Статус: 🟢 live — Streamlit-демо, открывается в браузере.

👀 **Что смотреть вживую:** как организованы вкладки по метрикам над одним списком сегментов; как показывают разброс/таблицы скоров; UX «для неинженеров» (загрузка файла → метрики → экспорт).

💬 **Совет:** прецедент для нашей строки вкладок-судей (`tabs(metric_names)` над общим списком абзацев). Смотри на *навигацию между вкладками* и не повторяй их слабое место — это reference-based offline-метрики (BLEU/COMET), без span-уровня и без живого редактирования. Нам нужна их структура вкладок, но содержимое вкладки у нас — LLM-судья со span-карточками, а не агрегатная цифра.

### 4. MT-LENS — ранжирование и двухуровневый контракт скоров

🔗 [github langtech-bsc/mt-evaluation](https://github.com/langtech-bsc/mt-evaluation)
Статус: 🟡 local (Gradio-тулкит, поднимать у себя).

👀 **Что смотреть вживую (или по README/скриншотам):** сортируемые посегментные таблицы [исходник, перевод, скор]; как разнесены «per-segment» и «aggregate» представления.

💬 **Совет:** отсюда — **двухуровневый контракт скоров**: бэкенд отдаёт только per-paragraph `{paragraph_id, score, spans[]}`, а агрегаты (mean/min/max, фильтрация, сортировка) считает фронт. Это архитектурное решение №2 в teardown — посмотри, как у них это разнесено, чтобы наш API не тащил агрегацию на бэк. Чего у них НЕТ и что добавляем мы — «прыжок к абзацу» из таблицы в редактор.

### 5. Synslator — двухпанельный редактор + термпанель

🔗 [arxiv 2310.05025](https://arxiv.org/abs/2310.05025) (см. §2.2, post-editing interface)
Статус: ⚪ paper-only — публичного UI нет, смотрим по рисункам в статье.

👀 **Что смотреть (в статье):** двухпанельная посегментная раскладка (панели справа от текста); сворачиваемая правая термпанель; как термины подсвечиваются по ходу post-editing.

💬 **Совет:** референс для *раскладки редактора* и *правой термпанели*. Поскольку живого демо нет — это «вдохновение по скриншотам», не более. Наш KG-слой богаче (ранжированные кандидаты + double-click-вставка канона + QID-якорь). Не трать много времени: возьми из статьи 1-2 рисунка раскладки и иди дальше.

### 6. Efficient-MT — MQM-схема карточек + GEMBA-DA скоринг

🔗 [github aixplain/Efficient-MT](https://github.com/aixplain/Efficient-MT) · [arxiv 2502.12755](https://arxiv.org/abs/2502.12755)
Статус: 🟡 local (без лицензии — код не трогаем, только паттерны).

👀 **Что смотреть вживую/в репо:** MQM-онтология (5 классов × 3 severity); формат вывода судьи; human-in-the-loop рекомендации правок.

💬 **Совет:** ключевой источник **MQM-схемы** — это решение №1 в teardown: все судьи отдают `{improved_translation, errors:{minor/major/critical:[{class,span}]}}`. Бери *структуру схемы*, а сам промпт переписывай из статьи GEMBA (у Efficient-MT нет лицензии). Главный риск у нас — «схема issues разъезжается» (промпты и runtime-tool-схема расходятся), и MQM как жёсткий контракт это лечит.

### 7. KG-MT / XC-Translate — KG-слой терминологии

🔗 [paper (EMNLP 2024)](https://aclanthology.org/2024.emnlp-main.914/) · [github apple/ml-kg-mt](https://github.com/apple/ml-kg-mt)
Статус: 🟡 local (Apple non-OSI — только паттерны и бенчмарк).

👀 **Что смотреть:** как QID-якорь (Wikidata) используется для перевода имён сущностей; таксономия типов сущностей; бенчмарк XC-Translate (CC BY-SA) и метрика m-ETA.

💬 **Совет:** обоснование нашего KG-слоя — они показывают, что LLM плохо переводят имена (GPT-4 ≈35% m-ETA). Бери QID-якорь и идею тиров, бенчмарк XC-Translate — для валидации точности, m-ETA — как метрику (переписать с нуля). **Открытый вопрос** (риск №2 в teardown): их подход общий, а наш KG привязан к русскому/всемирной истории (pymorphy3 — только русский). Это решение «RU→EN-only vs любая пара» надо принять — см. раздел ниже.

### 8. ViDove — upload→generate с batch-окном и памятью

🔗 [github pigeonai-org/ViDove](https://github.com/pigeonai-org/ViDove)
Статус: 🟡 local (GPL — только паттерны).

👀 **Что смотреть:** batch-окно (N сегментов в один вызов, window≈5); rolling-память последних N переводов в промпт; proofreader-агент.

💬 **Совет:** единственный прецедент для нашего **upload→generate**, но у них batch-механика (субтитры), а наша новизна — *живой* upload→edit→multi-judge цикл, которого нет ни у кого. Бери batch-окно + rolling-контекст как технику генерации, но не копируй их агентную обвязку. Это и есть контрибуция демо-трека — подчеркни в статье, что живого редактирования ни у кого нет.

### 9. TransAgents — настраиваемые LLM-агенты как «судьи»

🔗 [transagents.ai (live)](https://transagents.ai) · [github minghao-wu/transagents](https://github.com/minghao-wu/transagents)
Статус: 🟢 live.

👀 **Что смотреть вживую:** как конфигурируются роли/агенты; протоколы оценки MHP (Monolingual Human Preference) / BLP (Bilingual LLM Preference).

💬 **Совет:** прецедент для нашей идеи **user-configurable judges** (оценщик = декларативный объект `{id,label,color,model,prompt,api_key_ref}`). Смотри, как они дают пользователю задавать агентов. MHP/BLP — словарь протоколов оценки, который можно процитировать в Related Work. Их фокус — генерация (литературный перевод), наш — оценка; берём идею конфигурируемости, не пайплайн.

## Приоритет просмотра (совет Claude)

1. **Translation Canvas** (1) — ближайший прецедент карточек, ради *формы* карточки.
